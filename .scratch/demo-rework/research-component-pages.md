# Research: how the best libraries structure a component page

Question: what is the optimal structure for an umriss demo subpage (one per
component or feature, after the package's "Scenarios" page), and how should the
text in it be written?

Method: real pages opened on 2026-09-25 (WebFetch, and raw HTML / doc sources
where a site renders client-side). Where a page could not be read, it says so.

(headings are things a developer is trying to do), and all of them **name the
prop or option in the first sentence** of a section.

## 2. What the writing guides say

- **Diátaxis** — keep modes apart. Reference: *"Reference material is useful when it is consistent"*; it describes, it does not instruct or argue ([reference](https://diataxis.fr/reference/)). How-to: *"A how-to guide is concerned with work - a task or problem, with a practical goal"*; titles say exactly what is shown — good *"How to integrate …"*, bad *"Integrating …"*, very bad the bare noun ([how-to guides](https://diataxis.fr/how-to-guides/)). A component page is a legitimate mix, but **each section should be one mode**: examples = how-to, props = reference, "why" = explanation.
- **Google developer style** ([headings](https://developers.google.com/style/headings)) — sentence case; task headings start with a bare infinitive (*"Create an instance"*, not *"Creating…"*); conceptual headings are noun phrases; no code in headings.
- **Microsoft style** ([headings](https://learn.microsoft.com/en-us/style-guide/scannable-content/headings)) — *"Focus on what matters to customers … In most cases, don't talk about products, features, or commands in headings. Concentrate on what customers can achieve"*; parallel structure within a level; put the important word first; no two headings in a row without text.
- **GOV.UK** ([how we document](https://designnotes.blog.gov.uk/2018/11/05/how-we-document-components-and-patterns-in-the-gov-uk-design-system/)) — plain words over jargon; every visual example has a written description; say when *not* to use; state known issues.
- **NN/g** ([Design Systems 101](https://www.nngroup.com/articles/design-systems-101/)) — each component needs a unique name and *"a clear explanation for what this element is and how it is typically used, occasionally accompanied by do's and don'ts"*, plus attributes, states and code.

## 3. Patterns that matter (distilled)

1. **Everyone opens with one sentence.** The strong ones (Polaris, Fluent, Highcharts, React Aria, MUI X) put *what it is* and *when you reach for it* into sentence one or two. The weak ones (Chakra, Tremor) say only the category.
2. **Synonyms in the intro** (MUI X "sticky, frozen, locked"; AG Grid "Frozen Rows or Floating Rows") — cheap and it catches readers searching for another library's word.
3. **Alternatives are explicit** in every design system (GOV.UK, Carbon, Primer "When to use something else"), and absent in every dev library. The dev libraries are worse for it.
4. **Example text sits above the demo, visible.** Atlassian, GOV.UK, MUI, MUI X, Polaris, Ant (below, in a box). Nobody good hides the only explanation inside the code.
5. **Code is collapsed by default** on the pages that have the most examples (Mantine, Atlassian, GOV.UK). Tabs Preview/Code (shadcn, Chakra, Tremor) work for small demos.
6. **Example titles:** grid/scheduler docs and Radix Primitives use tasks; component galleries use feature nouns. Feature nouns are fine for *appearance* axes (Sizes, Variants); tasks are better for *behaviour* ("Pin the totals row").
7. **API goes at the end, per part, as a table** (Name / Type / Default / Description) — universal. Radix Themes is the only one putting it before examples.
8. **Accessibility:** Radix's keyboard table is the most useful artefact in the survey. Design systems give it a tab; dev libraries mostly omit it.
9. **Anatomy** appears when a component has parts (Radix JSX skeleton, Carbon/Primer diagram). For compound components it is the fastest orientation there is.
10. **Showcase pages** without prose (shadcn) look good and teach nothing; Polaris patterns (numbered callouts + "uses these components") teach how pieces fit.

## 4. Recommendation for umriss

The current shell (`packages/demo/src/Page.tsx`) already has the right bones:
rubric → name → one sentence → import line → Examples → API → "Why it is like
this". Keep them. The changes below are what the survey says is missing.

### 4.1 Subpage skeleton

```
Rubric (eyebrow)
H1  Component name
    Lede: 1–2 sentences (rules in 4.2)
    Import line (copy)
    [Hero demo — the first example, full width, no heading needed]

H2  Examples
    H3 per example: title, one visible lead sentence, live demo, code (collapsed)

H2  When to use something else          ← new, short, only if a real alternative exists
    2–4 bullets: "<situation> → <other component>" with links

H2  Keyboard                             ← new, only for interactive components
    Key | Action table (Radix style)

H2  API
    One table per exported part: Prop | Type | Default | Description

H2  Why it is like this                  ← existing; decisions, a11y reasoning, known limits
```

Order rationale: the reader comes to see it work (hero), to copy the case they
need (examples), to check it is the right tool (alternatives), then to look up a
prop (API). "Why" stays last: it is explanation, read once, not looked up.

Deliberately **not** tabs. Mantine/Carbon/Atlassian split into tabs because
they have a designer audience; umriss's reader is one developer, and one scroll
with a table of contents keeps Ctrl+F working.

Leave out (all seen elsewhere, none earn a place here):
- **Installation** per page — it is the same for every component; one place per package.
- **Features bullet list** (Radix) — it repeats the example titles.
- **Anatomy diagram** as its own section — the first example's code *is* the anatomy for compound components; if a component has 4+ parts, make the first example the minimal full skeleton and title it "Anatomy" or "All parts".
- **Do/Don't image pairs** — design-system furniture. A single "Don't" sentence inside an example lead does the same job at a fraction of the space.
- **Design tokens / Styles API / Semantic DOM** sections — umriss has no public styling API to document per component.
- **Changelog / "Recent changes"** per page — lives in the package changelog.
- **Accessibility as a separate appendix** — agree with the existing Page.tsx decision; reasoning goes in "Why", but the *keyboard table* is reference, not reasoning, so it earns its own section.

### 4.2 The lede (intro text)

Rules:
1. **Sentence 1 says what it does for the user of the screen, in plain words** — not what category it belongs to, not what it is built from.
2. **Sentence 2 (optional) says when to reach for it** or the one limit that matters (Polaris, Fluent, Mantine "opinionated").
3. **Max ~35 words total.** No "powerful", "flexible", "easy", "beautiful".
4. **Name the synonyms** a reader might search for, in parentheses, once (MUI X/AG Grid).
5. **No prop names** in the lede — they belong in example leads.
6. **No dash-joined afterthoughts.** Several current sentences end on "– and …"; that tail is usually an argument that belongs in "Why".

Good / bad:

- Bad: *"A powerful, flexible splitter component for building resizable layouts."* (category + adjectives, says nothing)
- Bad (current style): *"One place for density, portal target, toasts and language - and it stays optional, because every component already works without it."* (a list of contents, then a design argument)
- Good: *"Two panes with a draggable divider between them (also called a split view). Use it when the user needs both at once – a trend above its alarms, a list beside its detail."*
- Good: *"Pinned columns stay visible while the table scrolls sideways (also called frozen or sticky). Pin the identifying column and the totals; everything else scrolls."*

### 4.3 Section headings and example titles

- **Sentence case, no code in headings** (Google).
- **Appearance axes → noun** ("Variants", "Sizes", "Density").
- **Behaviour → imperative task**, starting with the verb (Google/Diátaxis): "Pin the totals row", "Load rows on demand", "Group tasks into lanes", "Show a target line". Not "Pinning", not "Row pinning", not "`pinned` prop".
- **Parallel form within a page**: either all tasks or nouns-then-tasks, never shuffled.
- **Order examples from simplest to richest** (matches the existing examples-ladder preference): default → common options → states (loading, empty, error, disabled) → composition with other umriss parts → the full, realistic case.
- **Always include the unhappy states** the domain needs: empty, loading, error, very long values, many rows. AG Grid, Atlassian ("Empty state", "Focus after row deletion") and Spectrum do; they are what data-dense apps hit first.

### 4.4 Per-example text

- **One visible lead sentence, above the demo, max ~25 words.** Today the explanation sits in a code comment inside collapsed code (`packages/core/demo/examples/Button/01-variants.tsx`) — that is invisible to the skimmer, which is exactly the reader who needs it. Lift it into the page (e.g. an exported `lead` next to `title`), keep only code-level remarks in the comment.
- The sentence **states the situation and names the prop**, Polaris + MUI X combined: *"Use when … Set `x` to …"*.
  - Good: *"Use `primary` once per surface – two main actions side by side are no longer a main action."*
  - Good: *"When the dataset is large, pass `rowCount` and load pages in `onRangeChange`; the table keeps scroll position while rows arrive."*
  - Bad: *"This example demonstrates the variants of the button."* (restates the title)
- **No second paragraph.** If an example needs one, it is either two examples or a "Why" entry.

### 4.5 Where code sits

- Directly **below** its demo, **collapsed by default**, with the page-level "open all" toggle the shell already has (Mantine/Atlassian/GOV.UK pattern). Keep this.
- Code must be the **complete, copyable file** that renders the demo (shell already guarantees this). No hidden wrapper, no elided imports.
- Data fixtures shared across examples: show as a second file tab (already supported via `shows`), never inline hundreds of rows.

### 4.6 API section

- One table per exported part, columns **Prop | Type | Default | Description** (universal).
- Description column is one line, **reference voice**: what it is, units, range. No advice (Diátaxis) — advice goes in an example lead.
- Group or visually de-emphasise inherited HTML props (React Aria's 250-row tables are the anti-example).
- Events/callbacks may be a second table for grid/schedule (AG Grid splits Attributes / Configuration / Events) — worth it for Table and Schedule, not for Button.

### 4.7 "Why it is like this"

- Keep: this is umriss's distinctive section, and Diátaxis explicitly wants explanation separated from reference.
- Headings in it are **statements** (as `why/meter.tsx` already does: "A fraction, not a percentage"). Good.
- Add a **"Known limits"** sub-heading where one exists (GOV.UK "Known issues", MUI "Limitations"). Honest scope ties back to ADR-0032/0035.

### 4.8 The Scenarios page (package overview)

Model on **Polaris patterns**, not shadcn Examples:

```
H1  Scenarios
    1 sentence: what these screens are (realistic, composed, copyable)

H2  <Scenario name as a job>          e.g. "Watch a line's alarms", "Plan a shift"
    1 sentence: who uses this screen and for what
    Live composed screen (full width)
    Numbered callouts on the screen → numbered list: "1 AlarmList – sorted by severity, …"
    "Built from:" linked list of the components used → their subpages
    Code (collapsed)
```

- Title scenarios by the **user's job**, not by the components ("Plan a shift", not "Schedule with Table").
- The **"Built from"** list is the navigation that makes the Scenarios page the entry to the subpages. MUI templates and Polaris both do this; shadcn does not and its Examples page is a dead end.
- 3–6 scenarios per package, most realistic first.

### 4.9 Checklist per subpage

- [ ] Lede ≤ 35 words: what it does + when; synonyms if any; no adjectives of praise
- [ ] First example is the minimal complete usage and needs no heading
- [ ] Example titles: nouns for appearance, imperative verbs for behaviour, sentence case
- [ ] Each example has one visible lead sentence naming the situation and the prop
- [ ] Empty / loading / error / overflow shown where the component can hit them
- [ ] "When to use something else" if a sibling component is often confused with it
- [ ] Keyboard table for anything focusable beyond a single button
- [ ] API tables one per part, reference voice only
- [ ] "Why" holds decisions and known limits, nothing a reader must know to use it
