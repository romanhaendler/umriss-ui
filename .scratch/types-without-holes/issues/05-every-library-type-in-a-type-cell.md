# 05: Every library type in a type cell is a link, and "Types on this page" defines the rest

Status: done
Blocked by: 01 (One table model, two writers), 02 (Rows that are true: no `never`, no free type parameters, constraints in the header)
Spec: `.scratch/types-without-holes/spec.md`

**What to build:** The reader records each type reference in a type cell whose declaration lies in this package or another workspace package; the cell renders as text segments, some of them links. A link goes to the type's props table (same page as an in-page anchor, otherwise to that page's address), otherwise to its definition in a new block **Types on this page** at the end of the API section. The block holds the closure of mentioned table-less types, in order of first appearance, stopping at types with a table; each entry has its name with parameters and constraints, its JSDoc, and a members table or its emitted declaration with library names linked; a type from another package names its package. Until the API index exists, the llms appendix prints every export that has neither a props table nor a definition block.

- [x] On a chart series page `Accessor<T>` links to its definition on the same page; on the table's Search page `TableRef` does, and inside it `TableSnapshot` is a link too.
- [x] llms fixture tests: a table-less type mentioned on a page gets a definition; the closure includes a type mentioned only inside a definition and stops at a type with a table; a type with a table on another page is a link, not a definition.
- [x] Built-site guard: every `#type-` link resolves to an element with that id on its target page, and every library type referenced in a type cell has a target.
- [x] Zero props name a library type with neither a table nor a reachable definition.
- [x] The definitions and links are in the prerendered HTML and in the llms text.
- [x] `ButtonSize`, `Accessor`, `TableRef`, `Wording`, `Intent` are defined in the llms text; `applyIntent`, `useTree`, `useToast`, `controlLimits` stand in the appendix with their declarations.

## Comments

Delivered. **The reader** (`packages/demo/src/tooling/propsReader.ts`) records each type a cell names on `PropEntry.references`. It resolves the name through the checker's symbol, and keeps only interfaces and aliases declared in source outside `node_modules`. Two declarations under one name throw, because one `#type-<Name>` cannot lead to two places. After the tables it reads the closure as definitions: every named type without a table, then what those name, in order of first appearance. Each is a `TypeEntry` with `definition: { description, from?, declaration?, references? }` and goes into `props.json` beside the tables. An interface, or an alias of an object literal, that has nothing but property members is drawn as a members table by `readType`. Anything else (a union, a function, a mapped or conditional type, an interface with methods such as `TableRef`) carries its declaration as written, without `export`. `readProps` now takes the package's compiler options (`compilerOptionsOf`/`readPackage` in `props.ts`, also used by `exportedDeclarations`). With the tsconfig `paths`, a neighbour's types are read from its source, not from a dist. The by-name `declarations` map and the free-parameter names are kept to the files given. `from` names the package of the nearest `package.json`.

**The model** (`apiTable.ts`) turns each named type in a type cell into a link span. `apiSection(page, pages, entries, eventsApart)` builds a page's tables and its definitions. A name links to its table (`#type-X` on the same page, `#/page/type-X` otherwise, written by the HTML as `../page/#type-X`). Failing that, it links to `#type-X` and the type is defined on this page. A name with neither stops the generator. The HTML writes the block `div.apiDefinitions` with `h3` "Types on this page", one `h4#type-X` per type, "From `@umriss-ui/core`." where it applies, the JSDoc as `p.apiProse`, then a members table or `pre.apiDeclaration` with the names linked. The Markdown writes `##### Types on this page` / `###### \`X\``, and its type cells as `` [`Accessor`](#type-Accessor)`<T>` ``. The app (`Page.tsx`), the prerendered page and the llms text all go through `apiSection`. `tablesOf` is gone. A twin's `#type-X` links become absolute, at the page's anchor. **The appendix** prints every export that no table and no definition explains. A component counts as explained by its `<Name>Props` table.

After rebasing onto props-table-hygiene 03, a definition counts as a reader's text. Its comment and its rows go through the same `check` as a table's rows. `linkedTables` turns its ADR numbers into links. Two charts type comments carried a requirement number (`ChartPerf`, `TooltipPoint`). Both numbers moved into `@remarks`.

Result: definitions in core 36, charts 21, table 45, schedule 19, calculation 5. `pnpm build:pages` passes the guard: 303 type links in the built site, all resolving. The `build-pages.mjs` guard checks every `references` entry against `props.json` and runs `typeLinkFaults` (`tooling/site.ts`) over every page. The llms texts grew: core 611 → about 680 kB, table 356 → about 398 kB.

After the rebase onto props-table-hygiene 01, `tableModel(entry, linkOf)` and `apiSection(page, pages, entries)` no longer take `eventsApart`, because the groups are decided by rule. The page's contents list takes its API entries from `apiSection`'s tables.

Baselines moved: none. No baseline shows an API section with a linked type; the Drawer table behind `drawer-beside-a-service-list` names no library type.

Deviations: (1) A definition's declaration is the declaration's source text without `export`, not a second `.d.ts` emit. For interfaces and aliases the two are the same text, and the reader has the node already. (2) In Markdown the declaration stands in a ```` ```ts ```` fence without links, because a fence cannot hold one. The names it uses are defined beside it, and the HTML links them. (3) "Neither a props table nor a definition" in the appendix counts a component's `<Name>Props` table as its own. Without that every component's function signature would join the appendix. (4) A type substituted into a helper's parameter (`EditOptions<Z[K]>`) is linked only where the helper's own member names it. Arguments carried in at the use are not followed; no such case exists today. (5) `Wording` (288 members) is drawn in full on the core pages that name it, as the spec's "the copy is generated" asks.
