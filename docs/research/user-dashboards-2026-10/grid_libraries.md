# Dashboard-grid libraries: layout models and what their users complain about (state 2026-10-13)

Method note. Issue lists, reaction counts, changelogs, READMEs and source excerpts were read on 2026-10-13 through the GitHub API (`gh api`), so counts are that day's. "+N" is the total reaction count on the issue's first post, "cN" the number of comments. Vendor docs were read through a summarising fetch tool; where only a search snippet was available it says so. Anything I recall but did not re-read today stands under Inferences or Gaps, never under Cited Findings.

## 1. What are the most frequent and most upvoted issues and requests in react-grid-layout and gridstack.js?

### Takeaway
In react-grid-layout (RGL) the upvoted complaints cluster around four things: the responsive layer (layouts that do not come back when widening, `measureBeforeMount`), compaction that cannot do "reading order" or a plain swap, item height that cannot follow content, and missing keyboard access. gridstack's tracker carries far fewer reactions (the top issue has 10), but the same themes appear in titles and in what the maintainer finally built: one-column mode removed as default in v10 "as too many new users had issues", and a list/reflow mode added in v14 after requests going back to 2017.

### Inferences
- The single most persistent wish in both trackers is not a new feature of the coordinate model but an escape from it: "reading order" reflow where a moved item is inserted and the rest shuffles along, as on a phone's home screen. RGL users asked from 2015 (#66) to 2022 and patched it themselves (#1100); RGL shipped `wrapCompactor` in Dec 2025; gridstack shipped `mode: 'list'` in Sep 2026. Two independent projects arriving at the same addition a decade in is strong evidence that end users expect a sequence.
- The many closed-by-stale-bot issues in RGL (#1222, #1201, #1612, #936) mean closed state says nothing about resolution before 2025; reactions are the better signal.
- gridstack's low reaction counts reflect its audience's habits (vanilla JS, Angular) and the maintainer's fast closing, not fewer problems; comment counts (#149 c50, #1094 c33) are the better proxy there.

## 2. How do RGL's responsive layer and gridstack's column options derive a layout for a narrower width, what do users report, and what did gridstack change in v10 to v14?

### Takeaway
RGL keeps one independent x/y/w/h layout per named breakpoint; a missing one is generated once by cloning the nearest larger breakpoint's layout, clamping it to the new column count and compacting, after which it lives its own life. gridstack keeps one layout plus cached per-column-count copies and re-derives narrower ones by a selectable rule (`moveScale`, `move`, `scale`, `list`, `compact`, `none`, or a function); it dropped the automatic one-column mode as default in v10 because it confused new users, and in v14 replaced the boolean `float` by four modes, two of which are sequence-based.

### Cited Findings

react-grid-layout
- Defaults: `breakpoints` `{lg: 1200, md: 996, sm: 768, xs: 480, xxs: 0}`, `cols` `{lg: 12, md: 10, sm: 6, xs: 4, xxs: 2}`; `layouts` is `Record<Breakpoint, Layout>`; feature list: "Responsive breakpoints", "Separate layouts per responsive breakpoint" — [README](https://github.com/react-grid-layout/react-grid-layout/blob/master/README.md)
- Columns are a fixed count per breakpoint that scale with the container width between breakpoints; since v2 the width must be passed in ("The grid no longer auto-measures width. Use the new `useContainerWidth` hook") — [CHANGELOG 2.0.0](https://github.com/react-grid-layout/react-grid-layout/blob/master/CHANGELOG.md)
- Generation rule, from the source of `findOrGenerateResponsiveLayout`: "If a layout exists for the breakpoint, returns a clone. Otherwise, generates a new layout from the nearest larger breakpoint." The code starts from `layouts[lastBreakpoint]`, prefers the first existing layout among the breakpoints at or above the target, then runs `correctBounds(clonedLayout, { cols })` and `compactor.compact(corrected, cols)` — [src/core/responsive.ts](https://github.com/react-grid-layout/react-grid-layout/blob/master/src/core/responsive.ts)
- "Does not come back when widening": #1222 (2020) "when you resize from small to larger, it seems to get stuck at that smaller breakpoint"; #1663 (2022) "when I grow it back through larger breakpoints, I see the items resize but then shrink down again". A user in #1663 (2023-08-22): "Honestly this is kind of a big problem and fix. Seriously. The npm.io description of this module is how it features break points over competing modules. This fix is for how break points don't reverse when first triggered." Another (2025-06-16): "Couple years this is still bugged." — [#1222](https://github.com/react-grid-layout/react-grid-layout/issues/1222), [#1663](https://github.com/react-grid-layout/react-grid-layout/issues/1663)
- User-found workarounds in those threads: remount with `key={breakpoint}`; or hold `layouts` in state and feed back what `onLayoutChange(layout, layouts)` reports — [#1663](https://github.com/react-grid-layout/react-grid-layout/issues/1663)
- Maintainer's closing note on #1663 (STRML, 2026-08-04, marked "This was generated by AI during triage"): "This is the v1 layout-cache bug and it's resolved in v2 when you keep the `layouts` prop in sync with `onLayoutChange` (the controlled pattern from the responsive-localstorage example)." — [#1663](https://github.com/react-grid-layout/react-grid-layout/issues/1663)
- 2.3.0 (2026-10-05) fix for #2110: "An item added at a smaller breakpoint through `data-grid` kept its small width when the container grew to a larger breakpoint. The generated layout cloned the smaller one and never re-read the size." — [CHANGELOG 2.3.0](https://github.com/react-grid-layout/react-grid-layout/blob/master/CHANGELOG.md)
- Other responsive-layer defects fixed only in v2: "Prevent infinite layout oscillation in toolbox pattern" (2.1.0); "Fix infinite re-render loop when passing inline objects as `layouts` prop" (2.1.1); `Maximum update depth exceeded` at fractional zoom (2.2.4); optional `debounceTimeout` for width updates "to avoid unnecessary repaints and broken layouts" (#2254, 2.3.0) — [CHANGELOG](https://github.com/react-grid-layout/react-grid-layout/blob/master/CHANGELOG.md)

gridstack

(default 12), breakpoints?: {w, c, layout?}[], breakpointForWindow? (default false = grid width), layout?: ColumnOptions }`. ### Inferences
- RGL's model makes every breakpoint a separate document. Because a generated layout is stored under its own key as soon as it exists, a later edit at `lg` does not reach `sm`: the user (or the developer) maintains up to five layouts. The tracker shows this as "order problem" (#1201, #1270), "shrinks in the bigger breakpoint" (#2110) and "add/remove with responsive localStorage" (#1529, #432). This follows from the source and README; no maintainer statement says it in these words.
- The "does not pop back" class of bug is a consequence of where the per-breakpoint state lives (inside the component unless the app mirrors it). The fix that worked for users is the controlled pattern, i.e. the application owns all layouts.
- gridstack's "one layout, derived views, cached per column count" is closer to what an end user expects, but the derivation is path-dependent by design (12 to 8 to 6 differs from 12 to 6, `compact` does not restore). - Both vendors' newest work (Grafana Auto grid, gridstack `mode: 'list'`, RGL `wrapCompactor`, Kibana's CSS-grid engine) moves toward CSS-grid-like flow with a column count that follows the width, and away from hand-kept coordinates per breakpoint.

## 3. Which libraries store an order rather than coordinates, and what do their users report about holes, packing and predictability?

### Takeaway
Muuri, Packery, dnd-kit sortable, Kendo TileLayout and Cloudscape Board keep a sequence (optionally with spans) and let an algorithm or CSS grid place it; RGL, gridstack and Syncfusion keep x/y/w/h (RGL and gridstack have recently added sequence-driven modes on top). Order-based packers are praised for natural reordering but draw complaints when the packing rule lets an item land somewhere the reader did not predict: Packery's most-reacted issue (+73) is exactly that.

### Cited Findings

Model matrix (verified parts only)
- react-grid-layout: stores `{ i, x, y, w, h, minW, maxW, minH, maxH, static, isBounded }` per item, one array per breakpoint; compactors `verticalCompactor` (default, "compact items upward"), `horizontalCompactor` ("leftward"), `noCompactor` ("free positioning"), `wrapCompactor` (extras, since 2.1.0: "paragraph-style layouts where items flow left-to-right and wrap to the next row"), custom via `Compactor { type, allowOverlap, preventCollision?, compact(layout, cols) }`; `preventCollision` blocks a move instead of pushing; `allowOverlap`; resize by handles (`resizeConfig.handles`, e.g. `["se","sw"]`) within min/max; 2.1.0 added `aspectRatioConstraint` and `positionConstraint`; persistence is the app's job via `onLayoutChange`, with two localStorage examples — [README](https://github.com/react-grid-layout/react-grid-layout/blob/master/README.md), [CHANGELOG](https://github.com/react-grid-layout/react-grid-layout/blob/master/CHANGELOG.md)

### Inferences
- The trade-off the trackers document: coordinate stores give exact, restorable placement but force a per-width answer and surprise users with gravity ("items jump up", "chases elements down the page"); order stores survive any width but must choose between a stable order with holes (Muuri default, gridstack `list`, CSS `grid-auto-flow: row`) and no holes with an unstable order (Muuri `fillGaps`, gridstack `compact`, CSS `dense`). gridstack's own doc comment states the second cost outright: "order isn't guaranteed to stay stable".
- Predictability during the drag matters as much as the end state: Packery's v2 change was made so that "It's easier to keep track of how items will move", and 73 reactions asked for the tight packing back. There is no packing rule that all users find natural once sizes differ; with equal sizes everyone agrees on insert-and-shift.
- Kendo and Cloudscape show the hybrid that avoids both extremes: an order plus spans, optionally a column start, placed by CSS grid.
- Order-based libraries without a size model (Muuri, Packery, dnd-kit) push resizing to the application, and their trackers then collect the resulting collision and measuring bugs (dnd-kit's variable-size issues).

### Gaps
- Kendo's `autoFlow` values (expected: `column`, `row`, `column dense`, `row dense`, per CSS `grid-auto-flow`) were not confirmed on the page read; a search snippet says the Angular default is `column`.
- No user reports on holes specifically for Kendo TileLayout, Syncfusion or Cloudscape were collected (their feedback portals were not searched, apart from one Telerik item under question 5).
- Cloudscape Board's column count per breakpoint and its exact reflow rule were not read (the docs page came back truncated).
- DevExtreme: I found no end-user dashboard-grid component in DevExtreme; the DevExpress "Dashboard" BI product arranges items in nested horizontal/vertical layout groups ([docs](https://docs.devexpress.com/Dashboard/116693/main-features/dashboard-layout)), which is a split-tree, not a grid. Absence in DevExtreme itself is unverified.
- AG Grid, PrimeReact, MUI and Mantine: not checked; I know of no first-party dashboard-grid component in any of them, which is recall, not evidence.

## 4. Is there a library with a fixed set of named sizes per item rather than free resize, and what do users say about free versus constrained resize?

### Takeaway
None of the surveyed libraries offers named sizes (small/medium/large) as a first-class concept; all model size as free column/row spans bounded by min/max, and the nearest things are Cloudscape's per-item default and minimum spans and Kendo's span-stepping keyboard resize. What users ask for is rarely "freer" resize: the upvoted requests are for sizes that follow content, lock an aspect ratio or stay fixed while only the position changes.

### Cited Findings
- RGL: per-item `minW`, `maxW`, `minH`, `maxH`, `static`; 2.1.0 added a "Pluggable Layout Constraints System" with `aspectRatioConstraint(16 / 9)` — nine years after #267 "Lock Aspect Ratio" (+11, 2016) — [CHANGELOG 2.1.0](https://github.com/react-grid-layout/react-grid-layout/blob/master/CHANGELOG.md), [#267](https://github.com/react-grid-layout/react-grid-layout/issues/267)
- RGL bug showing the cost of free resize with limits: "The preview stretched without limit during a resize, even with `minW`, `maxW`, `minH` or `maxH` set, and only snapped to the constraint on release" (fixed 2.2.3, 2026-03-24) — [CHANGELOG 2.2.3](https://github.com/react-grid-layout/react-grid-layout/blob/master/CHANGELOG.md)
- RGL content-driven size requests: #190 (+20), #971 (+14), #691 (+15), #1311 (+11), #1661 (+9) — see question 1 — [#190](https://github.com/react-grid-layout/react-grid-layout/issues/190), [#971](https://github.com/react-grid-layout/react-grid-layout/issues/971)
- RGL users with fixed-size items wanting only rearrangement: "This is feature I wanted, when you have static size grids layout just wanna exchange position double directions by user interaction." (2021-08-02); "I want a grid of 3 columns and 3 rows at all times. No matter what gets dragged where." (2020-09-15) — [#1100](https://github.com/react-grid-layout/react-grid-layout/issues/1100)
- gridstack: `noResize`, `locked`, min/max, `sizeToContent` (v9); 10.2.0 added "'r' to rotate during a drag" (swap w and h), with 10.2.1 "prevent 'r' rotation to items that can't resize (locked, noResize, fixed sizes)"; #1338 asks to keep item width when the column count changes — [CHANGES.md](https://github.com/gridstack/gridstack.js/blob/master/doc/CHANGES.md), [#1338](https://github.com/gridstack/gridstack.js/issues/1338)
- Cloudscape Board: each item type can declare `definition.defaultRowSpan`/`defaultColumnSpan` ("the number or rows the item will take when inserted to the board") and `minRowSpan` ("It can't be less than two. Defaults to two.")/`minColumnSpan`; resize announcements carry `isMinimalColumnsReached` and `isMinimalRowsReached` — [src/board/interfaces.ts](https://github.com/cloudscape-design/board-components/blob/main/src/board/interfaces.ts)
- Kendo TileLayout: `resizable` is `true | false | 'horizontal' | 'vertical'` per tile; keyboard resize steps "one column (to a maximum of the preset columns count)" / "one row" — [Tiles](https://www.telerik.com/kendo-react-ui/components/layout/tilelayout/tiles), [Keyboard navigation](https://www.telerik.com/kendo-react-ui-develop/components/layout/tilelayout/keyboard-navigation)
- Muuri has no resize: "this feature is best left outside Muuri's core" (niklasramo, 2020-01-22) — [haltu/muuri #356](https://github.com/haltu/muuri/issues/356)
- dnd-kit has no resize: #445 "Add drag/resizing" (+30, 2021, closed without implementation in Feb 2026 with a boilerplate note about the rewrite); #1127 "Resize - is it possible?" (c29) — [#445](https://github.com/clauderic/dnd-kit/issues/445), [#1127](https://github.com/clauderic/dnd-kit/issues/1127)

### Inferences
- A named-size model would be a differentiator: no established web library has it, although every platform the brief names as a model (phone home screens) does. The evidence that it would be welcome is indirect: requests for fixed sizes with rearrangement only, for content-driven height and for aspect locks all ask the library to take the size decision away from the drag handle.
- Free resize is also where the hard bugs live: handle direction (#1519, +20), handle drift (#2233, +12), bounds (#1779, +10; #1990, +15), touch resize (#1458, #2097), keyboard resize (question 5). A small set of sizes chosen from a menu removes this whole class and is trivially keyboard- and touch-operable.

### Gaps
- I found no user statement that directly compares free resize with a named-size picker in these trackers; the claim rests on adjacent requests.
- Products with named widget sizes (Apple WidgetKit families, Windows tiles, Home Assistant sections) are outside this note's scope and were not researched here.
- Smaller libraries that might offer size presets (e.g. Swapy, react-tiles-dnd, Salesforce or Atlassian internals) were not checked.

## 5. What is the state of keyboard and screen-reader support for moving and resizing items?

### Takeaway
Neither of the two market leaders can move or resize an item by keyboard as of October 2026: RGL has an open issue since 2023 and a maintainer note that it has "no keyboard/ARIA handling"; gridstack closed its 2017 accessibility issue as "very unlikely to get fixed" and has an unmerged keyboard PR since July 2025 that stalls on unequal item sizes. Keyboard arrangement exists where the model is a sequence with spans: Kendo TileLayout (documented shortcuts), Cloudscape Board (live announcements for reorder, resize and insert) and dnd-kit (keyboard sensor, with known trouble on variable sizes).

### Inferences
- The reason is structural, and gridstack's maintainer names it: with a pointer, a move is a continuous path and the library reacts at a halfway threshold; a key press is a discrete step, so the library must define what "one step right" means among items of unequal size and what gets displaced. Coordinate grids have no natural answer; a sequence does (previous/next), and spans give resize a natural unit. That is why Kendo's keyboard model is "swap with neighbour in order" and "one column wider".
- Kendo moves only along the order (Shift+Left/Right), with no up/down move; that is a limitation to weigh, since sighted keyboard users think in two dimensions. Cloudscape's announcements carry a `direction: "horizontal" | "vertical"`, which suggests two-dimensional keyboard moves there.
- Announcing "what was disturbed" (Cloudscape's `conflicts`/`disturbed`) is the only place in this survey where a library tells a screen-reader user about the side effects of a move. It is the bar to meet.
- For a new library, built-in keyboard move and resize with announcements is a gap in the open-source field as of late 2026, not table stakes: the two libraries with most users lack it, and procurement-driven users (Microsoft testers on RGL, Drupal on gridstack, the PR author "trying to get our application to comply to the a11y norm") have been asking for years.

### Gaps
- Cloudscape Board's actual key bindings and its docs' accessibility section were not read (page truncated); the keyboard claim rests on the announcement API and the operation types.
- dnd-kit's screen-reader announcements (live region, customisable messages) and whether the rewritten `@dnd-kit/react` 0.5 fixed #985 were not verified today; I recall the former from the legacy docs.
- Syncfusion Dashboard Layout keyboard support: not verified. I recall its accessibility page listing keyboard navigation as not supported for this component; treat as unconfirmed.
- Kendo's WAI-ARIA roles for tiles were not on the page read.

### Inferences
- RGL's two drag/resize dependencies are the root of several long-running complaints (findDOMNode warnings +20/+14/+8, touch `preventDefault`, handle drift fixed in react-resizable, no keyboard because the handle is react-resizable's bare span). A new library that owns pointer handling avoids inheriting them; react-draggable alone is about half of RGL's minified weight.
- React 19: RGL's peer range does not exclude it and I found no open React 19 issue, only #2045 (2024-05-29, a key warning, closed). That is absence of complaints, not a compatibility statement.
- Bus factor is one for both leaders (STRML, adumesny), and gridstack development is openly steered by sponsorship. Both facts argue against treating either as a foundation whose gaps will be closed upstream on request.
- Muuri and Packery should be read as sources of ideas (packing rules, drag feel), not as candidates.
