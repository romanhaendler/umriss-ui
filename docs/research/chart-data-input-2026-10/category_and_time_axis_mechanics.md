# Category and time axis mechanics in performance-oriented / canvas chart libraries (state: October 2026)

Versions examined (npm `latest` on 2026-10-10): ECharts 6.1.0, Chart.js 4.5.1 (+ chartjs-plugin-zoom 2.2.0), Highcharts 13.1.1, uPlot 1.6.32, d3-scale 4.0.2, Observable Plot 0.6.17, Lightweight Charts 5.2.1, SciChart.js 6.0.6 (docs read: v4 and v5 doc trees), LightningChart JS (`@lightningchart/lcjs`) 9.0.0.

Evidence labels used below: **[src]** = read in the tagged source file, **[doc]** = official documentation, **[issue]** = maintainer statement in an issue, **[summary]** = page content obtained through a summarising fetch/search tool (wording may not be verbatim), **[inferred]** = my reading, not stated by the source.

## 1. Internally: true band scale, or ordinal index on a linear scale?

### Takeaway
Every canvas library examined (ECharts, Chart.js, Highcharts, uPlot, Lightweight Charts, SciChart) represents a category as an integer index on an affine scale; "band" is only a half-unit padding of that linear extent. Only D3 and Observable Plot use a string-domain band scale, and even D3's band scale is an affine function of the domain index materialised into an array.

### Cited Findings
- **ECharts [src]**: `OrdinalScale` holds an `OrdinalMeta` (array `categories` + lazily built hash map string -> index) and "an interval LinearScaleMapper" with extent `[0, ordinalMeta.categories.length - 1]`; `parse` turns a string into its ordinal number via the map and rounds a number (`mathRound`), `normalize`/`scale` delegate to the linear mapper. The file header still reads "Linear continuous scale". — [Ordinal.ts 6.1.0](https://github.com/apache/echarts/blob/6.1.0/src/scale/Ordinal.ts#L129-L176)
- **ECharts [src]**: the band is not a scale property but an extent adjustment: with `boundaryGap: true` (`axis.onBand`) `makeExtentWithBands` shrinks the pixel extent by `size / count / 2` on each side, and `dataToCoord` is `linearMap(scale.normalize(scale.parse(data)), [0,1], makeExtentWithBands(this))`; `coordToData` is the inverse plus rounding. — [Axis.ts 6.1.0](https://github.com/apache/echarts/blob/6.1.0/src/coord/Axis.ts#L139-L151), [makeExtentWithBands](https://github.com/apache/echarts/blob/6.1.0/src/coord/Axis.ts#L274-L283)
- **ECharts [src]**: storage per dimension type is `'float': Float64Array, 'int': Int32Array, 'ordinal': Array, 'time': Float64Array`; on an ordinal dimension the raw strings in the chunk are overwritten by their ordinal numbers (`chunk[i] = ordinalMeta.parseAndCollect(chunk[i])`). — [DataStore.ts 6.1.0](https://github.com/apache/echarts/blob/6.1.0/src/data/DataStore.ts#L50-L57)
- **Chart.js [src]**: `CategoryScale.parse(raw, index)` returns an integer index into `labels`; `getPixelForValue` is `getPixelForDecimal((value - _startValue) / _valueRange)`, `getValueForPixel` is `Math.round(_startValue + decimal * _valueRange)`. With `offset: true`, `_startValue = min - 0.5` and `_valueRange = labels.length`, otherwise `min` and `labels.length - 1`. — [scale.category.js v4.5.1](https://github.com/chartjs/Chart.js/blob/v4.5.1/src/scales/scale.category.js#L70-L153)
- **Chart.js [doc]**: "the `category` scale uses integers as an internal format, where each integer represents an index in the labels array; but, if parsing is enabled, it can also parse string labels." — [data-structures.md v4.5.1](https://github.com/chartjs/Chart.js/blob/v4.5.1/docs/general/data-structures.md)
- **Highcharts [src]**: there is no category scale class. `axis.categories` is the option array, or `[]` when `type: 'category'` (`hasNames`); `Axis.nameToX(point)` returns a number x (index into `categories`, or into `names` via `namesMap`), which then flows through the ordinary linear translation. — [Axis.ts v13.1.1 nameToX](https://github.com/highcharts/highcharts/blob/v13.1.1/ts/Core/Axis/Axis.ts#L1739-L1781), [categories init](https://github.com/highcharts/highcharts/blob/v13.1.1/ts/Core/Axis/Axis.ts#L746-L764)
- **Highcharts [src]**: the "band" is `pointRange`: `seriesPointRange = hasCategories ? 1 : (series.options.pointRange ?? closestPointRange ?? 0)`, and `minPointOffset = seriesPointRange / 2` pads the axis by half a unit at each end ("to make room for points with a pointRange, typically columns, or line/scatter points on a category axis"). — [Axis.ts setAxisTranslation](https://github.com/highcharts/highcharts/blob/v13.1.1/ts/Core/Axis/Axis.ts#L1841-L1945)
- **uPlot [doc]**: no categories natively. "x-values must be numbers, unique, and in ascending order." "A scale's default distribution is linear `distr: 1`, but can be switched to indexed/evenly-spaced." — [docs/README.md 1.6.32](https://github.com/leeoniya/uPlot/blob/1.6.32/docs/README.md)
- **uPlot [src]**: `distr: 2` is typed "1: linear, 2: ordinal, 3: logarithmic, 4: arcsinh"; when the x scale is ordinal the library swaps in an index array for scaling (`_data0[i] = i`) and keeps the caller's `data[0]` only for tick labels ("in ordinal mode, scale range is by index ... but tick values are from data"). — [uPlot.js 1.6.32](https://github.com/leeoniya/uPlot/blob/1.6.32/src/uPlot.js#L1234-L1252), [uPlot.d.ts](https://github.com/leeoniya/uPlot/blob/1.6.32/dist/uPlot.d.ts#L638-L639)
- **uPlot [issue]**: the author's original recommendation for categories is exactly the caller-side lookup: "while the x-values have to be numeric, x labels can be text ... you could simply keep a map in app-space", with `data[0] = [0, 1, 2]` and `axes.x.values: vals => vals.map(v => xCats[v])`. — [uPlot #9](https://github.com/leeoniya/uPlot/issues/9)
- **uPlot [issue]**: later recommendation: "the easiest way is to set `distr: 2` on the x scale", with `data[0] = ['a', 'b', 'c']` and `axes[0].values: (u, splits) => splits`. — [uPlot #671](https://github.com/leeoniya/uPlot/issues/671#issuecomment-1073397387)
- **uPlot [src]**: the grouped/stacked bars demo passes `["Group A", "Group B", ...]` as `data[0]` with `time: false, distr: 2`, a custom `range`, `splits` and `values: u => u.data[0]`. — [bars-grouped-stacked.html](https://github.com/leeoniya/uPlot/blob/1.6.32/demos/bars-grouped-stacked.html), [grouped-bars.js](https://github.com/leeoniya/uPlot/blob/1.6.32/demos/grouped-bars.js)
- **Lightweight Charts [src]**: the horizontal scale is purely index-based: `indexToCoordinate(index) = width - (baseIndex + rightOffset - index + 0.5) * barSpacing - 1`; time enters only through `timeToIndex`, a `lowerBound` binary search over the sorted `_points`. — [time-scale.ts v5.2.1](https://github.com/tradingview/lightweight-charts/blob/v5.2.1/src/model/time-scale.ts#L430-L560)
- **SciChart.js [summary of doc]**: CategoryAxis "is a special axis type which uses the X-Index not the X-Value to measure chart series"; the axis overview classes axes as "Category and Value axis types" and lists a "Text / String Axis: Use LabelProviders to format axis labels as text". — [Category Axis](https://www.scichart.com/documentation/js/v4/2d-charts/axis-api/axis-types/category-axis/), [Axis API overview](https://www.scichart.com/documentation/js/v4/2d-charts/axis-api/axis-api-overview/)
- **D3 [src]**: `scaleOrdinal` keeps `index = new InternMap()` (value -> position) and `domain = []`; `scaleBand` is an ordinal scale whose range is computed as `values = sequence(n).map(i => start + step * i)` with `step = (stop - start) / max(1, n - paddingInner + paddingOuter * 2)` and `bandwidth = step * (1 - paddingInner)`; `scalePoint` is `band().paddingInner(1)`. Neither exposes an `invert`. — [band.js v4.0.2](https://github.com/d3/d3-scale/blob/v4.0.2/src/band.js), [ordinal.js v4.0.2](https://github.com/d3/d3-scale/blob/v4.0.2/src/ordinal.js)
- **Observable Plot [src/doc]**: builds real `scaleBand` / `scalePoint` / `scaleOrdinal` (band padding 0.1, point padding 0.5); "barY requires that the x scale is a band scale". — [scales/ordinal.js v0.6.17](https://github.com/observablehq/plot/blob/v0.6.17/src/scales/ordinal.js), [features/scales.md](https://github.com/observablehq/plot/blob/v0.6.17/docs/features/scales.md)

### Inferences
- The model umriss is asking about (strings in, integer positions inside, one affine scale) is not an exotic compromise; it is the mainstream implementation in ECharts, Chart.js and Highcharts. What these three add over umriss's current API is only (a) a string -> index map owned by the axis, (b) a default tick set at the integers with a label lookup, (c) a half-unit extent padding switch (`boundaryGap` / `offset` / `minPointOffset`).
- A D3 band scale is mathematically `start + step * indexOf(d)`; the difference to "ordinal on linear" is that the index is hidden behind a Map lookup and there is no inverse, so pointer -> category has to be re-derived by the caller (division by `step`).
- uPlot is the one library that sits where umriss sits today (numbers only, caller keeps the map), and its author moved from "keep a map in app-space" (2019) to "put the strings in `data[0]` and set `distr: 2`" (2022) — i.e. toward letting the library derive the index.

### Gaps
- LightningChart JS: its feature docs returned HTTP 403 to my fetches; I could not read how `BarChart` stores categories. Search-result summaries only say that `BarChart` is a separate chart type with category labels and that in `ChartXY` categorical labels are done with `AxisTickStrategies.Empty` plus `addCustomTick` — [bar docs](https://lightningchart.com/js-charts/docs/features/bar/), [BarChartCategoryLabels API](https://lightningchart.com/js-charts/api-documentation/v8.3.0/interfaces/BarChartCategoryLabels.html) (unverified).
- SciChart.js source is closed; statements rest on docs (v4/v5 doc trees, while npm latest is 6.0.6).

## 2. How is the category order determined; missing, duplicate and unused categories?

### Takeaway
Two regimes exist in each index-based library: an explicit list fixes order and extent (unused entries stay as empty slots, unknown names are dropped or fall back to a positional index), or categories are collected in order of first appearance across series. Sorting by default is a grammar-of-graphics trait (Plot), not a canvas-library one.

### Cited Findings
- **ECharts [src]**: without `axis.data` (`needCollect`), `parseAndCollect` appends each unseen category (`index = categories.length`) — order of first appearance over all series sharing the axis; with deduplication on, repeats resolve to the first index through the map. — [OrdinalMeta.ts 6.1.0](https://github.com/apache/echarts/blob/6.1.0/src/data/OrdinalMeta.ts#L98-L142)
- **ECharts [src]**: with an explicit `axis.data`, an unknown string yields `NaN` (the point is not placed), and a *number* in the category dimension is taken as an index directly — "only supported when !needCollect, because we should consider a common case: a value is 2017, which is a number but is expected to be tread as a category." — [OrdinalMeta.ts](https://github.com/apache/echarts/blob/6.1.0/src/data/OrdinalMeta.ts#L102-L139)
- **ECharts [src]**: "OrdinalScale extent should always originates from `[0, ordinalMeta.categories.length - 1]`, regardless of min/max of `series.data`" — listed-but-unused categories keep their slot. — [Ordinal.ts](https://github.com/apache/echarts/blob/6.1.0/src/scale/Ordinal.ts#L213-L221)
- **ECharts [doc]**: "If it is auto collected from series.data, Only the values appearing in series.data can be collected. For example, if series.data is empty, nothing will be collected." — [axis-common.md](https://github.com/apache/echarts-doc/blob/master/en/option/component/axis-common.md)
- **ECharts [src]**: deduplication can be switched off for large unique data ("category is ['2012-01-01', '2012-01-02', ...], where the input data has been ensured not duplicate and is large data"), skipping the map entirely; the option is read as `option.dedplication` in `createByAxisModel` (spelling as in source) while the comment names `axis.deduplication`. — [OrdinalMeta.ts](https://github.com/apache/echarts/blob/6.1.0/src/data/OrdinalMeta.ts#L78-L124)
- **ECharts [src]**: reordering categories at runtime (`realtimeSort`) needs two extra permutation arrays (`_ordinalNumbersByTick`, `_ticksByOrdinalNumber`) between ordinal number and tick position, including a pass for "`series.data` only covers part of the `axis.category.data`". — [Ordinal.ts](https://github.com/apache/echarts/blob/6.1.0/src/scale/Ordinal.ts#L62-L126)
- **Chart.js [src]**: `parse` first tests `labels[index] === raw` (positional fast path), else `labels.indexOf(raw)`; an unknown *string* is pushed onto `labels` (tracked in `_addedLabels` and removed again on `init`); if a label occurs more than once (`first !== last`) the data index is returned instead; the result is rounded and clamped to `[0, labels.length - 1]`. — [scale.category.js](https://github.com/chartjs/Chart.js/blob/v4.5.1/src/scales/scale.category.js#L4-L78)
- **Chart.js [doc]**: "If the `labels` property of the main `data` property is used, it has to contain the same amount of elements as the dataset with the most values." — [data-structures.md](https://github.com/chartjs/Chart.js/blob/v4.5.1/docs/general/data-structures.md)
- **Highcharts [src]**: with an explicit `categories` array the lookup is `names.indexOf(name)`; without it `namesMap[name] ?? -1`, and a miss appends (`x = names.length`) — first appearance across series; with explicit categories a miss falls back to `point.x` or `series.autoIncrement()` (#17438). — [Axis.ts nameToX](https://github.com/highcharts/highcharts/blob/v13.1.1/ts/Core/Axis/Axis.ts#L1739-L1781)
- **Highcharts [doc in src]**: `uniqueNames` (default true): "If the same point name is repeated in the same or another series, the point is placed on the same X position as other points of the same name. When false, the points are laid out in increasing X positions regardless of their names". — [AxisDefaults.ts v13.1.1](https://github.com/highcharts/highcharts/blob/v13.1.1/ts/Core/Axis/AxisDefaults.ts)
- **Highcharts [doc in src]**: "categories can also be extracted by giving each point a name and setting axis type to `category`. However, if you have multiple series, best practice remains defining the `categories` array." — [AxisDefaults.ts](https://github.com/highcharts/highcharts/blob/v13.1.1/ts/Core/Axis/AxisDefaults.ts)
- **D3 [src]**: `domain(_)` de-duplicates in order of appearance; an ordinal scale with implicit unknown grows its domain on first lookup; `band` sets `unknown(undefined)`, so an unlisted value returns `undefined`. — [ordinal.js](https://github.com/d3/d3-scale/blob/v4.0.2/src/ordinal.js), [band.js](https://github.com/d3/d3-scale/blob/v4.0.2/src/band.js#L6)
- **Observable Plot [src/doc]**: the inferred ordinal domain is `sort(values, ascendingDefined)` over an `InternSet` of all channel values — "the sorted union (all distinct values in natural order)"; more than 10,000 distinct position values throws `implicit ordinal domain ... has more than 10,000 values`; the `interval` option instead generates every slot between min and max ("show gaps for missing data"). — [ordinal.js inferDomain](https://github.com/observablehq/plot/blob/v0.6.17/src/scales/ordinal.js), [bar.md](https://github.com/observablehq/plot/blob/v0.6.17/docs/marks/bar.md)
- **uPlot [doc]**: one shared x array for all series; a series without a value at a position carries `null`; "If each series has data at arbitrary x-values, then the x-values array must be augmented with all x-values, and all y-values arrays must be augmented with `null`s". — [docs/README.md](https://github.com/leeoniya/uPlot/blob/1.6.32/docs/README.md)
- **Lightweight Charts [src]**: `DataLayer` unions the time points of all series in a `Map` keyed by time, sorts them, and assigns every point its `TimePointIndex`; an insertion in the middle re-indexes everything after it. — [data-layer.ts v5.2.1](https://github.com/tradingview/lightweight-charts/blob/v5.2.1/src/model/data-layer.ts#L131-L333)

### Inferences
- The three choices a library must make when it owns the map: (1) explicit list vs. collect; (2) on collect, first-appearance order — which makes the result depend on series order when series cover different categories (the reason Highcharts recommends the explicit array for multiple series); (3) what a number in a category position means (ECharts: index only if the list is explicit; Chart.js: index always; Highcharts: `x`).
- A number-valued category ("2017") is the recurring ambiguity of ordinal-on-linear: ECharts documents it in a source comment and resolves it by context, which its own maintainers call inconsistent (see section 8).
- For an internal sorted-array representation, "collect in first-appearance order" yields positions 0..n-1 that are sorted by construction for the first series only; a later series naming categories in another order produces unsorted x unless the library re-sorts per series or indexes by position (see section 6: Highcharts simply switches its sort requirement off on category axes).

### Gaps
- Not verified for Chart.js how a dataset that names an unknown category behaves across a full update cycle beyond the `_addedLabels` add/remove logic read in source.
- SciChart CategoryAxis: the docs I could read do not say which series defines the index; the v5 comparison table only marks "Multiple series with different point counts" as unsupported — [Discontinuous Date Axis](https://www.scichart.com/documentation/js/v5/2d-charts/axis-api/axis-types/discontinuous-date-axis/) [summary].

## 3. Mixed charts (bar + line on the same categorical axis)

### Takeaway
Because the category is a number, a line needs no special case: it is drawn at the same coordinate the bar group is centred on. Whether that is a band centre or a tick at the axis edge is decided by the axis padding switch, not by the series.

### Cited Findings
- **ECharts [src/doc]**: all series use `axis.dataToCoord`, which maps ordinal `i` into the band-shrunk extent, so a line point lies at the band centre when `boundaryGap` is true; the doc: default `true`, "labels and data appear only in the center part of two axis ticks, which is called *band*". — [Axis.ts](https://github.com/apache/echarts/blob/6.1.0/src/coord/Axis.ts#L139-L143), [axis-common.md](https://github.com/apache/echarts-doc/blob/master/en/option/component/axis-common.md)
- **ECharts [src]**: bars then take an offset from that centre: the layout returns `offsetCenter = offset + width / 2` per stack within the band. — [barGrid.ts 6.1.0](https://github.com/apache/echarts/blob/6.1.0/src/layout/barGrid.ts#L138-L143)
- **Chart.js [src]**: the bar controller overrides its index scale to `{type: 'category', offset: true, grid: {offset: true}}`; any element on that scale gets `getPixelForValue(index)`, i.e. the centre of the offset slot; grouped bars are placed at `range.start + range.chunk * stackIndex + range.chunk / 2` around it. — [controller.bar.js v4.5.1 overrides](https://github.com/chartjs/Chart.js/blob/v4.5.1/src/controllers/controller.bar.js#L284-L298), [_calculateBarIndexPixels](https://github.com/chartjs/Chart.js/blob/v4.5.1/src/controllers/controller.bar.js#L636-L666)
- **Highcharts [src]**: padding is the maximum over the series on the axis, and on a category axis every series contributes `pointRange = 1`, so a line alone on a category axis is also inset by half a category; `pointPlacement: 'on' | 'between'` removes or shifts that padding. — [Axis.ts](https://github.com/highcharts/highcharts/blob/v13.1.1/ts/Core/Axis/Axis.ts#L1866-L1911)
- **uPlot [src]**: bars are a path builder over the same aligned `data[0]`; `align` 0 centres the bar on the x value (`xShift = barWid / 2`), so a `linear` path series in the same chart passes through bar centres. — [paths/bars.js 1.6.32](https://github.com/leeoniya/uPlot/blob/1.6.32/src/paths/bars.js#L30-L60)
- **Lightweight Charts [src]**: every series type shares the index; the `+ 0.5` in `indexToCoordinate` puts the point in the middle of its `barSpacing` slot. — [time-scale.ts](https://github.com/tradingview/lightweight-charts/blob/v5.2.1/src/model/time-scale.ts#L551-L560)
- **Lightweight Charts [doc]**: "The library allocates specific width for each data point to maintain consistency between different chart types." — [time-scale.md v5.2.1](https://github.com/tradingview/lightweight-charts/blob/v5.2.1/website/docs/time-scale.md)

### Inferences
- With a true band scale (D3) the mixed case is the awkward one: the line has to add `bandwidth() / 2` itself, or use a second `scalePoint` kept in sync with the band's padding. With an index on a linear scale the centre is simply the value.
- umriss's current design already has this property; adding library-owned categories would not disturb it.

### Gaps
- I did not trace in Chart.js source which scale options win in a mixed chart whose first dataset is a line (whether `offset: true` is still applied); the statement above covers charts whose type or index scale comes from the bar defaults.
- Not verified how Observable Plot offsets point-like marks on a band scale.

## 4. How is bar width derived on category, linear and time axes?

### Takeaway
On a category axis the width is a fraction of one index unit, known without looking at data. On linear/time axes every library falls back to the smallest distance between x values, which requires a pass (and, where input may be unsorted, a sort) over all bar x values — and each maintainer flags that fallback as heuristic or as a bug source.

### Cited Findings
- **ECharts [src]**: category axis: `bandWidth = pxSpan / (scaleLinearSpan + (onBand ? 1 : 0))` ("Fix #2728, avoid NaN when only one data"). — [axisBand.ts 6.1.0](https://github.com/apache/echarts/blob/6.1.0/src/coord/axisBand.ts#L135-L155)
- **ECharts [src]**: numeric/time axis: `bandWidth = pxSpan / scaleLinearSpan * liPosMinGap`, where `liPosMinGap` is the "minimal positive gap of values (in the linear space) of all relevant series ... on this axis"; a single distinct value falls back to `pxSpan * 0.8`. — [axisBand.ts](https://github.com/apache/echarts/blob/6.1.0/src/coord/axisBand.ts#L157-L209), [axisStatistics.ts](https://github.com/apache/echarts/blob/6.1.0/src/coord/axisStatistics.ts)
- **ECharts [src]**: that metric copies every x value of every bar series on the axis into a temporary buffer and sorts it; source comments give "retrieving values above costs 40ms for 1e6 values in a certain platform" and for the typed-array sort "5ms for 1e6 values"; the result is cached per data preparation "to avoid repeated time-consuming calculation for large data (e.g., over 1e5 data items)"; computing it only for the visible window was rejected because it "would likely generate inconsistent result and bring jitter when dataZoom roaming". — [axisStatisticsMetricsImpl.ts 6.1.0](https://github.com/apache/echarts/blob/6.1.0/src/coord/axisStatisticsMetricsImpl.ts#L38-L140)
- **ECharts [src]**: within the band, bar width = `(bandWidth - barCategoryGap) / columns` adjusted by `barGap`; default `barCategoryGap = max(35 - stackCount * 4, 15) %`; `barWidth`/`barMaxWidth`/`barMinWidth` are percentages of `bandWidth`. — [barGrid.ts](https://github.com/apache/echarts/blob/6.1.0/src/layout/barGrid.ts#L165-L270)
- **Chart.js [src]**: `computeMinSampleSize` gathers all parsed index values of all visible bar datasets on the scale, sorts and de-duplicates them (cached in `scale._cache.$bar`), and takes the minimum pixel distance between consecutive values *and* between consecutive ticks; default bar size = `min * categoryPercentage (0.8)`, bar = `chunk * barPercentage (0.9)`. — [controller.bar.js](https://github.com/chartjs/Chart.js/blob/v4.5.1/src/controllers/controller.bar.js#L7-L82)
- **Chart.js [doc]**: `barThickness` unset: "the base sample widths are calculated using the smallest interval that prevents bar overlapping ... This mode always generates bars equally sized"; `'flex'`: widths "based on the previous and following samples ... generates bars with different widths when data are not evenly spaced"; a number: fixed pixels, percentages ignored. — [bar.md v4.5.1](https://github.com/chartjs/Chart.js/blob/v4.5.1/docs/charts/bar.md)
- **Highcharts [src]**: `categoryWidth = min(|xAxis.transA| * (ordinal.slope || options.pointRange || xAxis.closestPointRange || xAxis.tickInterval || 1), xAxis.len)`, then `groupPadding` and `pointPadding` as fractions; on a category axis `pointRange` is 1; on linear/datetime it is the closest x distance found during data processing. — [ColumnSeries.ts v13.1.1 getColumnMetrics](https://github.com/highcharts/highcharts/blob/v13.1.1/ts/Series/Column/ColumnSeries.ts), [Series.ts closestPointRange](https://github.com/highcharts/highcharts/blob/v13.1.1/ts/Core/Series/Series.ts#L2283-L2312)
- **uPlot [src]**: `findColWidth` scans the full x array for the smallest adjacent delta among points with defined y ("scan full dataset for smallest adjacent delta; will not work properly for non-linear x scales, since does not do expensive valToPosX calcs till end"); bar width = column width * `size[0]` (default `[0.6, inf, 1]` = factor, max px, min px). Adjacent deltas suffice because x is required sorted. — [paths/bars.js](https://github.com/leeoniya/uPlot/blob/1.6.32/src/paths/bars.js#L5-L50)
- **Lightweight Charts [src]**: no derivation: the slot width is the scale state `barSpacing` (default 6), changed by zooming. — [time-scale.ts](https://github.com/tradingview/lightweight-charts/blob/v5.2.1/src/model/time-scale.ts#L595-L640), [time-scale.md](https://github.com/tradingview/lightweight-charts/blob/v5.2.1/website/docs/time-scale.md)
- **D3 / Plot [src/doc]**: width is `bandwidth() = step * (1 - paddingInner)`; for bars on time Plot points away from bars altogether: "You can also make a time-series bar chart with a rect mark, possibly with the bin transform", or an ordinal scale with `interval`. — [band.js](https://github.com/d3/d3-scale/blob/v4.0.2/src/band.js#L20-L32), [bar.md](https://github.com/observablehq/plot/blob/v0.6.17/docs/marks/bar.md)

### Inferences
- umriss's rule ("a fraction of the smallest distance between consecutive x values") is the same rule as ECharts `liPosMinGap`, Chart.js `computeMinSampleSize`, Highcharts `closestPointRange` and uPlot `findColWidth`. With a sorted-x requirement it is a single O(n) pass (uPlot); without it, it costs a copy and a sort (ECharts, Chart.js).
- If categories map to consecutive integers inside the library, the minimum distance is 1 by construction, so the existing min-distance rule yields the band width with no special case — this is literally what Highcharts does (`hasCategories ? 1 : ...`).
- The min-distance rule has one well-known failure: a single outlier pair of close x values shrinks every bar; Chart.js additionally mixes tick distances into the minimum, ECharts takes the maximum of per-group minima.

### Gaps
- No measured cost for Chart.js `getAllScaleValues` (concat + sort + unique of all bar values) was found in docs or source.
- LightningChart and SciChart bar-width derivation not researched (closed source, docs not reachable / not read).

## 5. Zoom and pan on a categorical axis

### Takeaway
Zooming an index axis is zooming a linear axis whose window is then snapped to integers; the snapping and the half-unit padding are where the special-case code and the bug history sit.

### Cited Findings
- **ECharts [doc]**: "if an axis is set to be `category`, `startValue` could be set as `index` of the array of `axis.data` or as the array value itself. In the latter case, it will internally and automatically translate to the index of array"; `minValueSpan`: "In category axis it can be set as `5` to represent 5 categories." — [data-zoom.md](https://github.com/apache/echarts-doc/blob/master/en/option/component/data-zoom.md)
- **ECharts [src]**: the dataZoom window is computed in percent and value on the linear extent; "In 'time' and 'ordinal' scale, rounding by 0 is required"; "`scale.parse` can also round input for 'time' or 'ordinal' scale". — [AxisProxy.ts 6.1.0](https://github.com/apache/echarts/blob/6.1.0/src/component/dataZoom/AxisProxy.ts#L200-L310)
- **ECharts [src]**: `OrdinalScale.count()` "is different from `.getOrdinalMeta().length` when extent is specified by `xxxAxis.min/max` or by `dataZoom`" — band width follows the zoomed extent. — [Ordinal.ts](https://github.com/apache/echarts/blob/6.1.0/src/scale/Ordinal.ts#L321-L328)
- **ECharts [doc]**: "For a `dataZoom` is applied on a category axis, the extra margin is always added regardless of `dataZoom` range" (numeric axes only get it at the edges of the full window). — [axis-common.md](https://github.com/apache/echarts-doc/blob/master/en/option/component/axis-common.md)
- **ECharts [src]**: bars may overflow the band under zoom: "Series shapes may overflow `bandWidth` when ... `barWidth` is set as absolute pixel values and `dataZoom` is used". — [barGrid.ts](https://github.com/apache/echarts/blob/6.1.0/src/layout/barGrid.ts#L515-L527)
- **chartjs-plugin-zoom [src]**: category scales have their own handlers: zoom changes `min`/`max` by `integerChange(delta)` (at least one whole step), pan steps by whole labels once the drag exceeds `stepDelta = round(scaleLength / max(range, 10))`. — [scale.types.js v2.2.0](https://github.com/chartjs/chartjs-plugin-zoom/blob/v2.2.0/src/scale.types.js#L210-L262)
- **chartjs-plugin-zoom [issue]**: recurring fixes specific to category scales: "Pan not working for simple chart or category scale" ([#86](https://github.com/chartjs/chartjs-plugin-zoom/issues/86)), "Fix category scale Zoom/Pan proportion problems" ([#151](https://github.com/chartjs/chartjs-plugin-zoom/issues/151)), "Category scale pans while zooming" ([#190](https://github.com/chartjs/chartjs-plugin-zoom/issues/190)), "Fix zoom on category scale" ([#434](https://github.com/chartjs/chartjs-plugin-zoom/pull/434)), "pan category scales whose categories are narrower than a pixel" ([#949](https://github.com/chartjs/chartjs-plugin-zoom/pull/949)).
- **Chart.js [src]**: a zoomed category scale just slices: ticks are generated `for (value = min; value <= max; value++)`. — [scale.category.js](https://github.com/chartjs/Chart.js/blob/v4.5.1/src/scales/scale.category.js#L97-L114)
- **uPlot [issue]**: for the first bars implementation: "i disabled zooming, since i don't think there is a great use-case for it in charts like this and it adds to the requirement to handle it properly". — [uPlot #9 comment](https://github.com/leeoniya/uPlot/issues/9#issuecomment-591798181)
- **uPlot [src]**: with `distr: 2`, a requested scale min/max is converted to indices by binary search (`opts.min = closestIdx(opts.min, data[0])`). — [uPlot.js](https://github.com/leeoniya/uPlot/blob/1.6.32/src/uPlot.js#L2338-L2340)
- **Lightweight Charts [doc]**: zoom/pan state is a *logical range* of fractional indices: "The indices can have fractional parts ... the `5.2` index means that the fifth bar is fully visible, while the sixth bar is 20% visible"; `setVisibleRange` in time "cannot extrapolate time", the logical range can go "beyond the bounds of the available data". — [time-scale.md](https://github.com/tradingview/lightweight-charts/blob/v5.2.1/website/docs/time-scale.md)

### Inferences
- Two designs for the zoom window on an index axis: integer-snapped (ECharts, Chart.js plugin) or continuous in index space (Lightweight Charts). The continuous variant needs no category-specific zoom code at all; the snapped variant produced a dedicated code path and a long tail of fixes in the Chart.js plugin.
- For a library with an affine scale, zooming categories costs nothing new if the window is allowed to be fractional and bars are clipped.

### Gaps
- Highcharts zoom on a `categories` axis was not traced in source (whether extremes are snapped to integers).
- D3/Plot: no built-in zoom for band scales; not researched further (out of scope).

## 6. Time: accepted inputs, where parsing happens, cost, and the sorted-x requirement

### Takeaway
All libraries end at epoch numbers in a numeric array (ms everywhere except uPlot, Lightweight Charts and SciChart, which use seconds). They differ in whether the library converts (ECharts, Chart.js via adapter, Highcharts since date strings are accepted, Lightweight Charts for business-day strings) or refuses (uPlot), and each converting library documents a fast path that skips conversion when numbers are supplied. Sortedness is required by uPlot, Highcharts (non-category) and Lightweight Charts, detected and exploited by Chart.js, and not required by ECharts — which pays with linear scans.

### Cited Findings
- **ECharts [doc]**: on a time axis a value may be a string "that can be parsed by method `parseDate` in `echarts/src/util/number.ts`, e.g. `'2024-04-09 13:00:00'`", a timestamp number, or a `Date`. — [axis-common.md](https://github.com/apache/echarts-doc/blob/master/en/option/component/axis-common.md)
- **ECharts [src]**: conversion happens once when the data store is built: for a `time` dimension `value = +parseDate(value)` unless it is already a number ("spead up when using timestamp"; function marked "Performance sensitive"); `parseDate` uses its own regex because "Different browsers parse date in different way, so we parse it manually", treats strings without offset as local time, and uses `Date.UTC` otherwise. The result lives in a `Float64Array`. — [dataValueHelper.ts 6.1.0](https://github.com/apache/echarts/blob/6.1.0/src/data/helper/dataValueHelper.ts#L36-L73), [number.ts parseDate](https://github.com/apache/echarts/blob/6.1.0/src/util/number.ts#L502-L561)
- **ECharts [src]**: no sort requirement and no use of order: nearest-point lookup is a full loop (section 7) and the bar min-gap sorts a copy (section 4).
- **Chart.js [doc]**: "The time scale **requires** both a date library and a corresponding adapter to be present." "Chart.js uses timestamps defined as milliseconds since the epoch ... internally. However, Chart.js also supports all of the formats that your chosen date adapter accepts. You should use timestamps if you'd like to set `parsing: false` for better performance." — [time.md v4.5.1](https://github.com/chartjs/Chart.js/blob/v4.5.1/docs/axes/cartesian/time.md)
- **Chart.js [src]**: `parse(scale, input)`: optional user `parser` function, then "Only parse if it's not a timestamp already" -> `adapter.parse(value[, format])`, optional `adapter.startOf(value, round)`, returns `+value`. — [scale.time.js v4.5.1](https://github.com/chartjs/Chart.js/blob/v4.5.1/src/scales/scale.time.js#L46-L77)
- **Chart.js [src]**: sortedness is detected while parsing (`sorted = false` as soon as `cur[iAxis] < prev[iAxis]` or null) and stored as `meta._sorted`; with `parsing: false` the data is taken as-is and `_sorted = true` is assumed. — [core.datasetController.js v4.5.1](https://github.com/chartjs/Chart.js/blob/v4.5.1/src/core/core.datasetController.js#L451-L484)
- **Chart.js [doc]**: "Chart.js is fastest if you provide data with indices that are unique, sorted, and consistent across datasets and provide the `normalized: true` option to let Chart.js know that you have done so. Even without this option, it can sometimes still be faster to provide sorted data." "If parsing is disabled, data must be sorted and in the formats the associated chart type and scales use internally." — [performance.md](https://github.com/chartjs/Chart.js/blob/v4.5.1/docs/general/performance.md), [data-structures.md](https://github.com/chartjs/Chart.js/blob/v4.5.1/docs/general/data-structures.md)
- **Chart.js [src]**: without `normalized`, the time scale collects all timestamps of all datasets and runs `_arrayUnique(values.sort(sorter))`; with it, it reuses the first dataset's parsed values. — [scale.time.js getDataTimestamps/normalize](https://github.com/chartjs/Chart.js/blob/v4.5.1/src/scales/scale.time.js#L627-L674)
- **Highcharts [doc in src]**: "In a datetime axis, the numbers are given in milliseconds". — [AxisDefaults.ts v13.1.1](https://github.com/highcharts/highcharts/blob/v13.1.1/ts/Core/Axis/AxisDefaults.ts)
- **Highcharts [src]**: a string x is parsed: "If x is a string, try to parse it to a datetime" -> `this.chart.time.parse(xOption)`. — [Series.ts v13.1.1](https://github.com/highcharts/highcharts/blob/v13.1.1/ts/Core/Series/Series.ts#L1513-L1519)
- **Highcharts [doc]**: Error #15, "Highcharts expects data to be sorted": "This happens when creating a line series or a stock chart where the data is not sorted in ascending X order. For performance reasons, Highcharts does not sort the data, instead it requires that the implementer pre-sorts the data." — [Highcharts error 15](https://assets.highcharts.com/errors/15/) [summary]
- **Highcharts [src]**: why: "Unsorted data is not supported by the line tooltip, as well as data grouping and navigation in Stock charts (#725) and width calculation of columns (#1900)"; and `nameToX` sets `series.requireSorting = false`, i.e. category axes are exempt. — [Series.ts](https://github.com/highcharts/highcharts/blob/v13.1.1/ts/Core/Series/Series.ts#L2296-L2304), [Axis.ts](https://github.com/highcharts/highcharts/blob/v13.1.1/ts/Core/Axis/Axis.ts#L1750)
- **Highcharts [doc in src]**: `turboThreshold` (1000): beyond it "the Series class looks for data configurations of plain numbers or arrays of numbers. The first and last valid points are checked. If found, the rest of the data is assumed to be the same. This saves expensive data checking and indexing in long series". — [SeriesDefaults.ts v13.1.1](https://github.com/highcharts/highcharts/blob/v13.1.1/ts/Core/Series/SeriesDefaults.ts#L2486-L2505)
- **uPlot [doc]**: "By default, x-values are assumed to be unix timestamps (seconds since 1970-01-01 00:00:00) but can be treated as plain numbers via `scales.x.time = false`"; "this precision is rarely necessary on calendar-aware `time: true` scales"; ms via option `ms?: 1e-3 | 1` ("timestamp multiplier that yields 1 millisecond"). — [docs/README.md](https://github.com/leeoniya/uPlot/blob/1.6.32/docs/README.md), [uPlot.d.ts](https://github.com/leeoniya/uPlot/blob/1.6.32/dist/uPlot.d.ts#L366-L367)
- **uPlot [doc]**: listed under Non-Features: "No data parsing, aggregation, summation or statistical processing - just do it in advance." Data type is `AlignedData = TypedArray[] | [...]`. — [README.md 1.6.32](https://github.com/leeoniya/uPlot/blob/1.6.32/README.md), [uPlot.d.ts](https://github.com/leeoniya/uPlot/blob/1.6.32/dist/uPlot.d.ts#L220)
- **uPlot [issue/src]**: the helper for unaligned input sorts for the caller: "you don't need to pre-sort datasets if you use `uPlot.join()`, since it will always do this internally"; source: "output is sorted ASC on the joined field (table[0]) and duplicate join values are collapsed". — [uPlot #724](https://github.com/leeoniya/uPlot/issues/724#issuecomment-1198429014), [utils.js](https://github.com/leeoniya/uPlot/blob/1.6.32/src/utils.js#L518-L520)
- **Lightweight Charts [src]**: `Time = UTCTimestamp | BusinessDay | string` — "a UTCTimestamp, a BusinessDay, or a business day string in ISO format" (example timestamp `1529899200`, i.e. seconds); strings are converted in `preprocessData` (`convertStringsToBusinessDays`). No `Date` objects. — [types.ts v5.2.1](https://github.com/tradingview/lightweight-charts/blob/v5.2.1/src/model/horz-scale-behavior-time/types.ts#L44-L56), [horz-scale-behavior-time.ts](https://github.com/tradingview/lightweight-charts/blob/v5.2.1/src/model/horz-scale-behavior-time/horz-scale-behavior-time.ts#L93-L123)
- **Lightweight Charts [issue]**: unsorted or duplicate times fail an assertion: "Assertion failed: data must be asc ordered by time, index=3, time=1727077163.929, prev time=1727077163.929"; maintainer: "there are some data points which are either duplicates or multiple data points for the same timestamp". — [lightweight-charts #1700](https://github.com/tradingview/lightweight-charts/issues/1700)
- **SciChart.js [summary of doc]**: "All Linux Timestamp properties in scichart.js must be divided by 1,000 to go from milliseconds to seconds"; `DateTimeNumericAxis` is a "Value Axis with additional features for Dates and Time formatting". — [Category Axis](https://www.scichart.com/documentation/js/v4/2d-charts/axis-api/axis-types/category-axis/), [Axis API overview](https://www.scichart.com/documentation/js/v4/2d-charts/axis-api/axis-api-overview/)
- **LightningChart JS [summary of doc, unverified]**: date-time is a tick strategy on a numeric axis; values are "UTC timestamps, meaning timestamp = milliseconds since 1st January 1970"; a separate axis type `linear-highPrecision` is needed to zoom to millisecond ranges. — [axis docs](https://lightningchart.com/js-charts/docs/features/axis/), [DateTimeTickStrategy v9.0.0](https://lightningchart.com/js-charts/api-documentation/v9.0.0/classes/DateTimeTickStrategy.html)
- **Observable Plot [src]**: strings that look like dates on an ordinal scale trigger a warning: "some data associated with the x scale are strings that appear to be dates (e.g., YYYY-MM-DD). If these strings represent dates, you should parse them to Date objects." — [scales.js v0.6.17](https://github.com/observablehq/plot/blob/v0.6.17/src/scales.js#L252-L296)

### Inferences
- Accepting `Date` and ISO strings while keeping a Float64Array is compatible in every converting library: conversion is a one-time O(n) materialisation step with a `typeof value === 'number'` fast path. ECharts is the closest precedent to umriss's "materialise once into parallel Float64Arrays" (`'time': Float64Array`).
- The real cost of string dates is semantic, not CPU: ECharts wrote its own parser to avoid browser differences and chose local time for offset-less strings; Chart.js externalised the whole problem into adapters and made the adapter mandatory; Lightweight Charts restricts strings to calendar days. A `Date` object has none of these ambiguities (`+date` is unambiguous).
- Sorted input: libraries that require it (uPlot, Highcharts, Lightweight Charts) state performance as the reason and report violations (docs / error 15 / assertion). Chart.js shows a middle path — detect during the materialisation pass and fall back to a slower lookup.

### Gaps
- No library publishes a measured parse cost for date strings at scale; the only numbers found are ECharts' source comments for value retrieval and sort (section 4).
- Lightweight Charts' validator file could not be fetched at the tag; the assertion text is quoted from the issue report, not from source.
- Whether Highcharts accepts `Date` objects as x (as opposed to numbers and strings) was not verified.

## 7. Hit-testing / nearest-point lookup on category axes

### Takeaway
On an index axis the pointer -> category step is arithmetic (`round` of the inverse affine map) in every library; what differs is the second step, index -> data point: array index (uPlot, Lightweight Charts, Chart.js when sorted), binary search (Chart.js, uPlot, Lightweight Charts on time), k-d tree (Highcharts), or a full scan (ECharts, Plot).

### Cited Findings
- **Chart.js [src]**: `getValueForPixel(pixel) = Math.round(_startValue + getDecimalForPixel(pixel) * _valueRange)`. — [scale.category.js](https://github.com/chartjs/Chart.js/blob/v4.5.1/src/scales/scale.category.js#L151-L153)
- **Chart.js [src]**: interaction uses "binary search when possible": only if the axis is the dataset's index axis and `metaset._sorted`; otherwise "Default to all elements, when binary search can not be used" (`{lo: 0, hi: data.length - 1}`). — [core.interaction.js v4.5.1](https://github.com/chartjs/Chart.js/blob/v4.5.1/src/core/core.interaction.js#L14-L64)
- **ECharts [src]**: `coordToData` rounds to the ordinal (`getRawOrdinalNumber(mathRound(mapper.scale(val)))`), but then `Series.indicesOfNearest` loops over the whole store calling `axis.dataToCoord` per item — commented "Performance-sensitive on large data (triggered by `tooltip`/`axisPointer` frequently)". — [Ordinal.ts](https://github.com/apache/echarts/blob/6.1.0/src/scale/Ordinal.ts#L193-L195), [Series.ts indicesOfNearest](https://github.com/apache/echarts/blob/6.1.0/src/model/Series.ts#L472-L518)
- **Highcharts [src]**: "Build the k-d-tree that is used by mouse and touch interaction to get the closest point. Line-like series typically have a one-dimensional tree where points are searched along the X axis". — [Series.ts buildKDTree](https://github.com/highcharts/highcharts/blob/v13.1.1/ts/Core/Series/Series.ts#L4070-L4079)
- **uPlot [src]**: cursor index = `closestIdx(valAtPosX, data[0], i0, i1)`, a binary search bounded by the visible index window; exposed as `valToIdx` / `posToIdx`. — [utils.js closestIdx](https://github.com/leeoniya/uPlot/blob/1.6.32/src/utils.js#L4-L23), [uPlot.js](https://github.com/leeoniya/uPlot/blob/1.6.32/src/uPlot.js#L2586-L2592)
- **uPlot [src]**: for grouped bars the demo does not use the cursor index but fills a quadtree with every drawn rect and tests `pointWithin` on hover. — [grouped-bars.js](https://github.com/leeoniya/uPlot/blob/1.6.32/demos/grouped-bars.js)
- **Lightweight Charts [src]**: `coordinateToIndex(x) = Math.ceil(_coordinateToFloatIndex(x))`, optionally followed by `_findNearestIndexWithData` when `ignoreWhitespaceIndices` is set; time -> index is `lowerBound`. — [time-scale.ts](https://github.com/tradingview/lightweight-charts/blob/v5.2.1/src/model/time-scale.ts#L575-L585)
- **Observable Plot [src]**: the pointer interaction scans every index of the mark for the minimum distance. — [interactions/pointer.js v0.6.17](https://github.com/observablehq/plot/blob/v0.6.17/src/interactions/pointer.js#L149-L159)
- **D3 [src]**: band and point scales have no `invert`. — [band.js](https://github.com/d3/d3-scale/blob/v4.0.2/src/band.js)

### Inferences
- If categories become integers 0..n-1 in one shared sorted array, umriss's existing binary search keeps working unchanged, and for categories it degenerates to `round(invert(px))` — a direct array index, as in Lightweight Charts and uPlot with `distr: 2`.
- The case that breaks index arithmetic is a series that does not cover all categories or lists them in another order: then position `i` is not row `i`. Libraries handle it either by forcing a shared, aligned x column with nulls (uPlot, Lightweight Charts' merged index), or by giving up order-based lookup (ECharts full scan; Highcharts k-d tree with `requireSorting = false`).
- With uPlot `distr: 2` and strings in `data[0]`, the search runs on the substituted index array, not on the strings [inferred from the `scaleData` swap at uPlot.js L1234-L1241].

### Gaps
- I found no maintainer statement quantifying ECharts' linear `indicesOfNearest` on large series.

## 8. What maintainers say about the cost of supporting both; regrets and bugs

### Takeaway
Named costs fall into four groups: ambiguity of numbers on a category axis (ECharts), bar-width heuristics on continuous axes (ECharts, Chart.js, uPlot), code size and special-casing of interaction (uPlot, Chart.js zoom plugin), and misuse of ordinal scales for temporal data (Plot). No maintainer statement was found that regrets index-on-linear as such; the regrets attach to the edges.

### Cited Findings
- **ECharts [src comment]**: on string coercion of categories: "There are two inconsistent behaviors in the current impl: Force conversion is applied on the case `xAxis{data: ['aaa', 'bbb', ...]}`, but no conversion applied to the case `xAxis{data: [{value: 'aaa'}, ...]}` and the case `dataset: {source: [['aaa', 123], ...]}` ... Since there's no sufficient good solution to offset cost of the breaking change, we preserve the current behavior, until real issues is reported." The same comment notes that "a number input represents an `OrdinalNumber` (i.e., an index)" and that coercion makes `NaN/null/undefined` in data equal the strings `'NaN'/'null'/'undefined'`. — [OrdinalMeta.ts](https://github.com/apache/echarts/blob/6.1.0/src/data/OrdinalMeta.ts#L40-L63)
- **ECharts [src comment]**: bars on non-category axes: "The layout on non-'category' axis relies on `bandWidth`, which is calculated based on the `linearPositiveMinGap` of series data. This strategy is somewhat heuristic and will not be public to custom series until required in future." — [barGrid.ts](https://github.com/apache/echarts/blob/6.1.0/src/layout/barGrid.ts#L111-L119)
- **ECharts [src comment]**: "Currently `bandWidth` can not be specified by users explicitly. But if we allow that in future ... Can only allow specifying a band width in data scale rather than pixel. LogScale needs to be considered". — [axisBand.ts](https://github.com/apache/echarts/blob/6.1.0/src/coord/axisBand.ts#L64-L81)
- **ECharts [issue]**: a 2020 request to size bars by a time window on a time axis was answered by a contributor with "Please consider using custom series" and closed as stale. — [echarts #12198](https://github.com/apache/echarts/issues/12198)
- **ECharts [src]**: features that do not cross over: "Do not support break in OrdinalScale yet"; `getMinorTicks` on ordinal: "Not support". — [Ordinal.ts](https://github.com/apache/echarts/blob/6.1.0/src/scale/Ordinal.ts#L149-L154)
- **Chart.js [issue]**: "Bar chart with linear time scale produces inconsistent bar width" — maintainer: "Duplicates #4666 (and many more), fixed by #4994". — [Chart.js #5306](https://github.com/chartjs/Chart.js/issues/5306)
- **Chart.js [src comment]**: the category scale must override `getPixelForTick` "because it calls getPixelForValue and category scale can have duplicate values"; and "For backward compatibility, vertical category scale reverse is inverted." — [scale.category.js](https://github.com/chartjs/Chart.js/blob/v4.5.1/src/scales/scale.category.js#L120-L149)
- **uPlot [issue]**: on adding bars with category labels: "adding this would not impact perf since this will be able to use the existing `data` structure and not add new mem allocations ... the main question here is one of additional code size. my gut feeling is that it can be done for an additional 1-3k with no perf impact, and that's a worthwhile trade-off to me." Also: "my goal is to extract as much value out of the current core as possible while maintaining the current perf, keeping a uniform API without hacks"; "i have already rejected features like scatter plots, which do not fit neatly into the current design." — [uPlot #9](https://github.com/leeoniya/uPlot/issues/9#issuecomment-547094824)
- **uPlot [issue]**: a contributor on the first bars attempt: "The approach to get the X axis labels to align horizontally with each group of bars is... creative :) I'm adding an extra stop to the min/max range, then positioning each group of bars 50% left." — [uPlot #9 comment](https://github.com/leeoniya/uPlot/issues/9#issuecomment-590289541)
- **uPlot [doc]**: the price of ordinal distribution on time: "Keep in mind that this will prevent logical temporal tick baselines such as start of day or start of month." And of the aligned format: "This format has implications that can make uPlot an awkward choice for multi-series datasets which cannot be easily aligned along their x-values." — [docs/README.md](https://github.com/leeoniya/uPlot/blob/1.6.32/docs/README.md)
- **Highcharts [src]**: references to the issues that motivated the rules: categories lookup "(#2522)", fallback to `point.x` "#17438", Y-axis categories "(#1784)", column width on unsorted data "(#1900)", ordinal padding "#988, #1853". — [Axis.ts](https://github.com/highcharts/highcharts/blob/v13.1.1/ts/Core/Axis/Axis.ts#L1727-L1778), [Series.ts](https://github.com/highcharts/highcharts/blob/v13.1.1/ts/Core/Series/Series.ts#L2296-L2304)
- **Observable Plot [src]**: the library warns when dates land on a band scale: "Dates are typically associated with a "utc" or "time" scale rather than a "band" scale. If you are using a bar mark, you probably want a rect mark with the interval option instead"; likewise for numeric strings. — [scales.js](https://github.com/observablehq/plot/blob/v0.6.17/src/scales.js#L252-L296)
- **Observable Plot [doc]**: "Use caution with high-cardinality ordinal domains ..., as rounding can lead to "wasted" space or even zero-width bands." — [features/scales.md](https://github.com/observablehq/plot/blob/v0.6.17/docs/features/scales.md)
- **SciChart.js [summary of doc]**: v5 added `DiscontinuousDateAxis` because CategoryAxis lacks "Multiple series with different point counts", "Multiple points at same x-value", "Points between base values" and "True time positioning"; advice: "Always specify `dataGap` when possible to avoid auto-calculation overhead." — [Discontinuous Date Axis](https://www.scichart.com/documentation/js/v5/2d-charts/axis-api/axis-types/discontinuous-date-axis/)

### Inferences
- The bug history clusters around three things a library owning the category map has to decide explicitly: (1) what a *number* means on a category axis; (2) duplicates; (3) series with different category coverage. None of these arises from the affine scale itself.
- The true-band-scale side has its own documented costs: no inverse, a hard cardinality ceiling (Plot throws above 10,000), rounding artefacts, and a warning system to steer users away from putting time on it.
- uPlot's author judged the internal cost of categories on the numeric core as code size only ("1-3k"), with no performance impact — the closest available statement to umriss's question from a maintainer with the same architecture.

### Gaps
- No conference talk or blog post by ECharts, Chart.js or Highcharts maintainers on this specific design choice was found within the search budget; the account rests on source comments, docs and issues.
- Referenced Highcharts issue numbers (#2522, #1900, #17438 ...) were not opened individually.

## 9. "Ordinal time" / gap-removing axes and their relation to category axes

### Takeaway
A gap-removing time axis is a category axis whose categories are timestamps: positions are array indices, the label comes from the timestamp at that index, and value -> position is a binary search. The libraries that started there (Lightweight Charts, SciChart CategoryAxis) later needed escape hatches for unequal point counts; the libraries with a continuous time axis added piecewise maps (Highcharts `ordinal`, Chart.js `timeseries`, ECharts `breaks`, SciChart `DiscontinuousDateAxis`).

### Cited Findings
- **Highcharts [doc in src]**: "In an ordinal axis, the points are equally spaced in the chart regardless of the actual time or x distance between them. This means that missing data periods (e.g. nights or weekends for a stock chart) will not take up space in the chart." "In stock charts the X axis is ordinal by default, unless the boost module is used and at least one of the series' data length exceeds the boostThreshold." — [AxisDefaults.ts v13.1.1](https://github.com/highcharts/highcharts/blob/v13.1.1/ts/Core/Axis/AxisDefaults.ts)
- **Highcharts [src]**: implemented as a transform pair on a linear axis: `val2lin(val)` finds the index of `val` in `ordinal.positions` (`getIndexInArray`) and returns `slope * index + offset`; `lin2val` is the inverse; outside the known positions the index is extrapolated from the average slope. The overhead is skipped for evenly spaced data: "Check if we really need the overhead of mapping axis data against the ordinal positions. If the series consist of evenly spaced data any way, we don't need any ordinal logic." — [OrdinalAxis.ts v13.1.1](https://github.com/highcharts/highcharts/blob/v13.1.1/ts/Core/Axis/OrdinalAxis.ts#L755-L862), [beforeSetTickPositions](https://github.com/highcharts/highcharts/blob/v13.1.1/ts/Core/Axis/OrdinalAxis.ts#L1050-L1150)
- **Highcharts [src]**: ordinal feeds straight into column width (`xAxis.ordinal?.slope` is the first candidate for `categoryWidth`) and into axis padding (`ordinalCorrection = ordinal.slope / closestPointRange`). — [ColumnSeries.ts](https://github.com/highcharts/highcharts/blob/v13.1.1/ts/Series/Column/ColumnSeries.ts), [Axis.ts](https://github.com/highcharts/highcharts/blob/v13.1.1/ts/Core/Axis/Axis.ts#L1914-L1921)
- **Chart.js [doc/src]**: "for the time series scale, each data point is spread equidistant"; it builds a lookup table of `{time, pos}` and interpolates by binary search (`_lookupByKey`) in both directions. — [timeseries.md](https://github.com/chartjs/Chart.js/blob/v4.5.1/docs/axes/cartesian/timeseries.md), [scale.timeseries.js v4.5.1](https://github.com/chartjs/Chart.js/blob/v4.5.1/src/scales/scale.timeseries.js#L1-L80)
- **uPlot [doc]**: `distr: 2` "is useful when you'd like to squash periods with no data, such as weekends" — the same switch its author recommends for string categories (section 1). — [docs/README.md](https://github.com/leeoniya/uPlot/blob/1.6.32/docs/README.md)
- **Lightweight Charts [src/doc]**: index-only by construction (section 1); visible range is offered both as data range (times) and logical range (indices); "The horizontal scale can also represent price or other custom values" through a pluggable horizontal-scale behaviour whose contract is `key(item) -> number`, `convertHorzItemToInternal`, `preprocessData`. — [time-scale.md](https://github.com/tradingview/lightweight-charts/blob/v5.2.1/website/docs/time-scale.md), [ihorz-scale-behavior.ts v5.2.1](https://github.com/tradingview/lightweight-charts/blob/v5.2.1/src/model/ihorz-scale-behavior.ts)
- **SciChart.js [summary of doc]**: "The CategoryAxis collapses the gaps and treats each datapoint as equidistant, ignoring the X-Value"; it "won't draw without" data or `defaultXStart`/`defaultXStep` or `defaultXValues`, because positions come from data indices. — [Category Axis](https://www.scichart.com/documentation/js/v4/2d-charts/axis-api/axis-types/category-axis/)
- **SciChart.js [summary of doc]**: v5 `DiscontinuousDateAxis` "interpolates data based on a fixed timescale after each baseValue"; base values "default to x-values from the first data series"; "Data points falling between baseValues are positioned proportionally within that segment". — [Discontinuous Date Axis](https://www.scichart.com/documentation/js/v5/2d-charts/axis-api/axis-types/discontinuous-date-axis/), [What's new 5.0](https://www.scichart.com/documentation/js/v5/whats-new/sdk-5.0/)
- **ECharts [doc]**: v6 `axis.breaks`: "Each entry represents a collapsed or skipped range of the axis"; a break maps `[start, end]` to `[start, start + gap]` in the data domain; "Axis breaks cannot be used in category axes". — [axis-common.md](https://github.com/apache/echarts-doc/blob/master/en/option/component/axis-common.md)
- **ECharts [src]**: breaks make the bar min-gap more expensive because every value passes through `scale.transformIn` first ("PENDING: time-consuming if axis break is applied"). — [axisStatisticsMetricsImpl.ts](https://github.com/apache/echarts/blob/6.1.0/src/coord/axisStatisticsMetricsImpl.ts#L104-L122)
- **Observable Plot [doc]**: the mirror-image move: an ordinal scale with `interval` to "enforce uniformity and show gaps for missing data" in a time-series bar chart. — [bar.md](https://github.com/observablehq/plot/blob/v0.6.17/docs/marks/bar.md)

### Inferences
- All gap-removing designs are compositions `pixel = affine(g(x))`: `g` is "index of x in a sorted array" (Highcharts ordinal, Lightweight Charts, uPlot `distr: 2`, SciChart CategoryAxis), a piecewise-linear table (Chart.js timeseries, SciChart DiscontinuousDateAxis) or a piecewise break map (ECharts). A string category axis is the same composition with `g` = "index of the name in a list". One mechanism — an optional value -> position map in front of the affine scale — therefore covers both categories and ordinal time, and uPlot exposes exactly one switch for both.
- Because `g` for ordinal time is a binary search over a sorted array and for categories a hash lookup done once at materialisation, the per-frame path stays affine over a Float64Array of positions in both cases.
- The limitation that recurs with pure index axes is multi-series alignment (SciChart's comparison table; uPlot's aligned-data caveat; Lightweight Charts' merged, re-indexed time points). A library that maps categories to positions per chart rather than per series avoids it for categories, since the list is finite and shared.

### Gaps
- Whether ECharts plans breaks on category axes: only "not yet" in source, no roadmap statement found.
- Apache Superset was not examined: it renders through ECharts and adds nothing at the level of axis mechanics [inferred, not verified].
- LightningChart JS gap handling on date-time axes not researched (docs unreachable).
