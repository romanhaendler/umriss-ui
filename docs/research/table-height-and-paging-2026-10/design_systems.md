# Design systems: paging, empty states and tables in fixed frames (state 2026-10-30)

Method note. Everything was read on 2026-10-30. Where a system publishes its guideline text in a repository (Carbon's website MDX, PatternFly's site markdown, Polaris' and Primer's doc MDX), I read that text through the GitHub API; component defaults come from the systems' own source (GitHub, or the published npm tarball for `@atlaskit/dynamic-table` 19.3.8 and `lightning-base-components` 1.28.19-alpha). Cloudscape's pages are rendered on the client, so I pulled the guideline text out of the rich-text payload the page ships; Spectrum's guidelines come from the HTML fragments its pages load. Atlassian, GOV.UK, Microsoft Support and Airtable were read through a summarising fetch tool. The quotes are exact as far as that tool returns them. Material 2's current site is client-rendered only, so its guidelines were read from the Wayback copy of 2019-05-28. Salesforce's developer docs return 403 to every fetch; their claims are marked [S] (search snippet only). Fluent 2's guideline site (fluent2.microsoft.design) and Google's Sheets help could not be read. They stand under Gaps. Anything I recall but did not re-read today stands under Inferences or Gaps, never under Cited Findings.

## 1. Pagination, scrolling or "load more": when does each system use which? (a)

### Takeaway
Cloudscape, Carbon, Primer, PatternFly, Material 2, Polaris (web), GOV.UK and Atlassian all prefer pagination to infinite scroll for large collections. Cloudscape argues for it outright: "We strongly recommend using pagination to give users easy and consistent access to all items without scroll". It allows progressive loading ("Load more") only for nested child rows. GOV.UK forbids infinite scroll. The scrolling, virtualised camp is component-led: Fluent v8 DetailsList has no pager at all, Carbon for IBM Products' Datagrid, Salesforce's `lightning-datatable` and React Spectrum's TableView all offer infinite scroll, and every one of them needs a container of definite height. Polaris splits by platform: buttons on the web, infinite scroll on iOS and Android. The systems disagree on one thing that matters to us: whether a pager is drawn when everything fits on one page. Cloudscape says always draw it. Atlassian, Primer and GOV.UK say hide it.

### Cited Findings
- Cloudscape (table view pattern): "There are two ways to show additional data in tables: pagination and progressive loading. Use pagination for organizing large datasets into manageable chunks … Use progressive loading when your user needs to see all the data in one view, to compare large data sets … For example, loading more child rows in a table with expandable rows." — [table view](https://cloudscape.design/patterns/resource-management/view/table-view/)
- Cloudscape (table): "Don't use progressive loading when pagination will work. Pagination provides several advantages over progressive loading, such as page load time and quicker access to specific items." / "Don't use pagination and progressive loading at the same time, except in tables with expandable rows." / "Don't use sticky header for continuous scrolling. We strongly recommend using pagination to give users easy and consistent access to all items without scroll." — [table usage](https://cloudscape.design/components/table/?tabId=usage)
- Cloudscape: "Only use filtering, pagination, and sorting if there are more than five items in the table." — [table usage](https://cloudscape.design/components/table/?tabId=usage); "Don't use pagination if the majority of your users operate on really small collection (less than five elements)." — [pagination](https://cloudscape.design/components/pagination/?tabId=usage)
- Cloudscape: "Display the pagination even if the resources set fits in one page." — [table view](https://cloudscape.design/patterns/resource-management/view/table-view/)
- Cloudscape has an "Open end pagination" variant "for cases when it's impossible to determine the full size of the data set", and suggests "jump to page … typically when datasets exceed 9 pages" — [pagination](https://cloudscape.design/components/pagination/?tabId=usage)
- Carbon: pagination is used "When it could take a considerable amount of time to load the available data at once or in a scrolling view", "When there is too much data to display on one page or within one view of a component", "To optimize on-page real estate" — [pagination usage](https://carbondesignsystem.com/components/pagination/usage/) ([MDX](https://github.com/carbon-design-system/carbon-website/blob/main/src/pages/components/pagination/usage.mdx))
- Carbon loading pattern: "A Load more option can be used to extend a list where only a small fraction of options are displayed" — [loading pattern](https://carbondesignsystem.com/patterns/loading-pattern/) ([MDX](https://github.com/carbon-design-system/carbon-website/blob/main/src/pages/patterns/loading-pattern/index.mdx))
- Carbon for IBM Products Datagrid: "Infinite scroll is supported via the `useInfiniteScroll` hook … can also be used to support virtualized data, this is required when working with large amounts of data" — [Datagrid docs page](https://github.com/carbon-design-system/ibm-products/blob/main/packages/ibm-products/src/components/Datagrid/Datagrid.docs-page.jsx)
- Fluent v8 DetailsList: virtualised. "By default, the List used within DetailsList will use the `body` element as the scrollable element", or the nearest element marked `data-is-scrollable="true"` — [DetailsListBestPractices.md](https://github.com/microsoft/fluentui/blob/master/packages/react-examples/src/react/DetailsList/docs/DetailsListBestPractices.md). Fluent v9 ships no pagination package: `packages/react-components` contains `react-table` and `react-skeleton` but nothing called pagination — [repo listing](https://github.com/microsoft/fluentui/tree/master/packages/react-components)
- Atlassian: "Use pagination when there are too many results to show on one page", and what counts as too many depends on "system load times", "the amount of data in each entry" and "the available screen space" — [pagination usage](https://atlassian.design/components/pagination/usage). In `@atlaskit/dynamic-table`, `rowsPerPage` defaults to `Infinity`, and the pager is rendered only when `totalPages > 1` (source comment: "only show pagination if there's MORE than 1 page") — [npm package](https://www.npmjs.com/package/@atlaskit/dynamic-table), `dist/es2019/components/stateless.js`
- Primer: "Use pagination to accommodate tables with a large dataset … Pagination also helps with performance" — [data table](https://primer.style/components/data-table) ([MDX](https://github.com/primer/design/blob/main/content/components/data-table.mdx)). Its pagination guidelines say "Every page should have a URL" and "If the content is only long enough for a single page, don't render pagination." — [pagination MDX](https://github.com/primer/design/blob/main/content/components/pagination.mdx)
- Polaris: "On the web, pagination uses buttons to move back and forth between pages. On iOS and Android, pagination uses infinite scrolling." / "Only be used for lists with more than 25 items" / on mobile "Start loading items when merchants are close to the bottom, roughly 5 items from the end" — [pagination MDX](https://github.com/Shopify/polaris/blob/main/polaris.shopify.com/content/components/navigation/pagination.mdx). Polaris React is archived, and Polaris Web Components shipped on 2025-10-01 — [repo README](https://github.com/Shopify/polaris). The web-components table paginates through `paginate`, `hasNextPage` and `hasPreviousPage` (previous/next only), and says "Use pagination for datasets with more than 50-100 rows" — [s-table](https://shopify.dev/docs/api/app-home/polaris-web-components/layout-and-structure/table)
- GOV.UK: "Only break up content onto separate pages if it improves the performance or usability of your service." / "Avoid using the 'infinite scroll' technique to automatically load content when the user approaches the bottom of the page." / "Do not show pagination if there's only one page of content." — [pagination](https://design-system.service.gov.uk/components/pagination/)
- Material 2: "Pagination controls provide swift access to all pages, while indicating that more pages exist." — [M2 data tables, archived 2019-05-28](https://web.archive.org/web/20190528005308/https://material.io/design/components/data-tables.html)
- Salesforce `lightning-datatable`: infinite loading is built in (`enableInfiniteLoading`, a `loadmore` event, `DEFAULT_LOAD_MORE_OFFSET = 20` px), and there is no pager — [lightning-base-components](https://www.npmjs.com/package/lightning-base-components), `src/lightning/datatable/infiniteLoading.js`. Salesforce's performance guide recommends infinite loading or LIMIT/OFFSET paging for big tables, and says performance is best "with a maximum of 1,000 rows and 5 columns" [S] — [data table performance](https://developer.salesforce.com/docs/platform/lwc/guide/data-table-performance.html)
- React Spectrum TableView: "Use the `loadingState` and `onLoadMore` props to enable async loading and infinite scrolling." — [TableView](https://react-spectrum.adobe.com/TableView). The Spectrum guideline fragments for table say nothing about paging — [behaviors](https://spectrum.adobe.com/fragments/components/table/behaviors), [usage guidelines](https://spectrum.adobe.com/fragments/components/table/usage-guidelines)
- PatternFly makes paging the default for normal tables. Its compact table is for when you "don't want to use pagination", and the striping guidance lists "Virtualized tables (no pagination)" — [table design guidelines](https://www.patternfly.org/components/table/design-guidelines) ([md](https://github.com/patternfly/patternfly-org/blob/main/packages/documentation-site/patternfly-docs/content/components/table/table.md))

### Inferences
- *(inference)* Every system that offers infinite scroll in a table also requires a frame of definite height (section 6). Paging is the choice for tables that sit in page flow. So option (2) of the design question, "only scrolling tables fill", matches how these systems actually split the work.
- *(inference)* The one-page-pager disagreement matters for a filled frame. If umriss follows Cloudscape (pager always visible), the frame's layout stays the same at 0, 5 or 100 rows, which is the umriss "pager does not jump" principle. If it follows Primer, Atlassian or GOV.UK, a five-row table would have no pager, and the space it leaves becomes blank.

### Gaps
- Fluent 2's guideline site would not render for any fetch, so I could not check whether it says anything about paging.
- The SLDS guidelines (lightningdesignsystem.com) say nothing on paging on the v1 data-table page — [v1 data tables](https://v1.lightningdesignsystem.com/components/data-tables/). The SLDS 2 guideline pages were not found.

## 2. Page-size options and defaults; is a page-size selector recommended? (b)

### Takeaway
No system computes page size from the space available. Page size is set by the team (Polaris, Primer, Atlassian) or chosen by the user and stored (Cloudscape, PatternFly, Carbon's advanced pagination, Material 2). The defaults gather around 10 to 25: PatternFly 10 (options 10/20/50/100), Carbon's story 10 (10/20/30/40/50), Material 2's example 10, Primer's guidance "20 rows is a good place to start" (its component defaults to 25), and Cloudscape's guidance "based on how much time it takes to load the data". Polaris paginates only beyond 25 or 50 items. Cloudscape and PatternFly put the selector in user preferences and ask that it persist between visits.

### Cited Findings
- Cloudscape: "The user can choose how many items are shown per page. You can set the default number of items, based on how much time it takes to load the data." — [collection preferences](https://cloudscape.design/components/collection-preferences/?tabId=usage). Also "Users can change the default number of table rows per view on Resources preferences" — [table view](https://cloudscape.design/patterns/resource-management/view/table-view/). And "Store all the table preferences, including column widths, when the user leaves the page and restore them when the user comes back" — [table usage](https://cloudscape.design/components/table/?tabId=usage)
- Cloudscape: selection must be reset on "pagination, sorting, filtering, page size changes" — [table usage](https://cloudscape.design/components/table/?tabId=usage)
- Carbon: "Advanced pagination is accompanied by an option that enables the user to change the number of items per page and to jump to a specific page number." — [data table MDX](https://github.com/carbon-design-system/carbon-website/blob/main/src/pages/components/data-table/usage.mdx). The guidelines give no numbers. The React story uses `pageSizes: [10, 20, 30, 40, 50]` — [Pagination.stories.js](https://github.com/carbon-design-system/carbon/blob/main/packages/react/src/components/Pagination/Pagination.stories.js). The component falls back to the first entry when the page size given is not in the list — [Pagination.tsx](https://github.com/carbon-design-system/carbon/blob/main/packages/react/src/components/Pagination/Pagination.tsx)
- PatternFly: the per-page selector is part of both full and compact pagination ("Used to choose the number of items displayed on a single page at once"). Indeterminate pagination "replaces the total page number in the per-page selector with a general label of 'many'" — [pagination guidelines](https://github.com/patternfly/patternfly-org/blob/main/packages/documentation-site/patternfly-docs/content/components/pagination/pagination.md). The default options are 10/20/50/100, and `perPage` defaults to the first — [Pagination.tsx](https://github.com/patternfly/patternfly-react/blob/main/packages/react-core/src/components/Pagination/Pagination.tsx)
- Primer: "Don't put too many or too few rows per page … These factors make it difficult to recommend an 'ideal' page size for all use cases, but 20 rows is a good place to start." The factors it lists are filtering, number of columns, visual complexity and "Amount of context needed" — [data table MDX](https://github.com/primer/design/blob/main/content/components/data-table.mdx). The component itself defaults to `pageSize = 25` and has no page-size selector — [Pagination.tsx](https://github.com/primer/react/blob/main/packages/react/src/DataTable/Pagination.tsx)
- Polaris: IndexTable and ResourceList should "Paginate when the current list contains more than 50 items" — [index-table MDX](https://github.com/Shopify/polaris/blob/main/polaris.shopify.com/content/components/tables/index-table.mdx), [resource-list MDX](https://github.com/Shopify/polaris/blob/main/polaris.shopify.com/content/components/lists/resource-list.mdx). The pagination guidance says "more than 25 items" — [pagination MDX](https://github.com/Shopify/polaris/blob/main/polaris.shopify.com/content/components/navigation/pagination.mdx). Neither has a page-size selector.
- Material 2: the pager displays "Number of rows per page"; example "Ten rows per page are displayed, with a total of 100 rows." — [M2 archived](https://web.archive.org/web/20190528005308/https://material.io/design/components/data-tables.html). MDC's pagination helps the "user change the rows per page (page size)", with 10 selected in the markup — [mdc-data-table README](https://github.com/material-components/material-components-web/blob/master/packages/mdc-data-table/README.md)
- Atlassian: there is no selector, and `rowsPerPage` is set by the team — [npm package](https://www.npmjs.com/package/@atlaskit/dynamic-table) `types.d.ts`: "Use this to control how many rows should be displayed per page. If the number of rows exceed one page, this will enable pagination."
- Salesforce: the performance guide suggests loading no more than 50 rows at a time when infinite loading [S] — [data table performance](https://developer.salesforce.com/docs/platform/lwc/guide/data-table-performance.html)
- GOV.UK: "How many items per page" is not covered — [pagination](https://design-system.service.gov.uk/components/pagination/)

### Inferences
- *(inference)* Option (1), page size from height, is not in any of these systems. Cloudscape and PatternFly treat page size as a stored user choice. Primer wants "Every page should have a URL". A page size that follows the frame would change on every resize, so "page 3" would not mean the same rows from one moment to the next, and a stored choice would be overridden. If umriss does option (1), it would be its own invention and should at least keep the first visible row in view when the size changes.
- *(inference)* Cloudscape's reason for its default ("how much time it takes to load the data") and Primer's factors (columns, complexity, context) are both about the data. None of them is about the frame.

### Gaps
- Not covered: Fluent (no pager), Spectrum, GOV.UK.

## 3. Where the pager sits, whether it is fixed, and the range text (c)

### Takeaway
The pager goes below the table almost everywhere. Carbon forbids putting it above. PatternFly puts full pagination both above (in the toolbar) and below, and makes the bottom one sticky on mobile. Cloudscape gives the table its own `pagination` slot, ties it to filtering (without filtering or header actions, the pager moves into the header's actions), and shows the total as a counter after the title rather than as a range. The range text is the same idea everywhere: Carbon "1–10 of 100 items", PatternFly "1 - 10 of N items", Material 2 "1‑10 of 100", Primer "1‒25 of N". Only PatternFly documents a sticky pager.

### Cited Findings
- Carbon: "The pagination component is always placed at the bottom of the data table." — [data table MDX](https://github.com/carbon-design-system/carbon-website/blob/main/src/pages/components/data-table/usage.mdx); "the pagination should be stacked and below the table with no padding between them" / "Do not stack the pagination component above the data table." — [pagination usage](https://carbondesignsystem.com/components/pagination/usage/). The default `itemRangeText` is `` `${min}–${max} of ${total} items` ``, and there is a `pagesUnknown` mode — [Pagination.tsx](https://github.com/carbon-design-system/carbon/blob/main/packages/react/src/components/Pagination/Pagination.tsx). At the small breakpoint "The select components have been removed … but information on the total number of items, items being displayed, and previous and next buttons remain." — [pagination MDX](https://github.com/carbon-design-system/carbon-website/blob/main/src/pages/components/pagination/usage.mdx)
- PatternFly: "For desktop views, place full pagination above the content it controls ('top pagination'), typically within a toolbar." / "Also place full pagination below the component it controls" / "On mobile, bottom pagination is center-aligned and sticky by default." On mobile, top pagination collapses to "A non-interactive count of items currently displayed." — [pagination guidelines](https://github.com/patternfly/patternfly-org/blob/main/packages/documentation-site/patternfly-docs/content/components/pagination/pagination.md). The toggle text is `{firstIndex} - {lastIndex} of {itemCount} items` — [ToggleTemplate.tsx](https://github.com/patternfly/patternfly-react/blob/main/packages/react-core/src/components/Pagination/ToggleTemplate.tsx)
- Cloudscape: the table has `pagination` and `preferences` slots in its header. "Don't use the pagination and preferences slots if the table doesn't have filtering or header actions. Instead, add pagination and preferences to the actions slot in the header component." The item counter is "a number next to the title that shows the total number of items … For example: (150)", with "+" when the total is unknown, and "If the table is in loading state, don't display the item counter." A "View all" link goes in the footer — [table usage](https://cloudscape.design/components/table/?tabId=usage). The compact pages variant "displays the current page and total number of pages as a single counter … For example, 1 of 3." — [pagination](https://cloudscape.design/components/pagination/?tabId=usage)
- Cloudscape: the sticky header carries "filtering, and using pagination" along with it; "Consider using a sticky header in your table when it has more than 30 items per page" — [table usage](https://cloudscape.design/components/table/?tabId=usage)
- Material 2: "Pagination is placed at the bottom of a table." It shows "Total number of rows, including the range currently in view" — [M2 archived](https://web.archive.org/web/20190528005308/https://material.io/design/components/data-tables.html); MDC markup "1‑10 of 100" — [mdc-data-table README](https://github.com/material-components/material-components-web/blob/master/packages/mdc-data-table/README.md)
- Primer: "Place pagination at the end of the page content." — [pagination MDX](https://github.com/primer/design/blob/main/content/components/pagination.mdx); range is drawn as `{start}‒{end} of {totalCount}` and announced as "Showing {start} through {end} of {totalCount}" — [Pagination.tsx](https://github.com/primer/react/blob/main/packages/react/src/DataTable/Pagination.tsx)
- Atlassian: "Pagination is a control that sits at the bottom of the page"; at most seven page links on small screens and 14 on large ones — [pagination usage](https://atlassian.design/components/pagination/usage); "the pagination component appears at the end of the table" — [dynamic table](https://atlassian.design/components/dynamic-table/usage)
- Polaris: "Be placed at the bottom of a long list that has been split up into pages" — [pagination MDX](https://github.com/Shopify/polaris/blob/main/polaris.shopify.com/content/components/navigation/pagination.mdx); IndexTable `pagination` "Properties to enable pagination at the bottom of the table." — [IndexTable.tsx](https://github.com/Shopify/polaris/blob/main/polaris-react/src/components/IndexTable/IndexTable.tsx)
- GOV.UK: "Add the pagination component after the content on each page that you're paginating." It has no range text, only a page title such as "Search results (page 1 of 4)" — [pagination](https://design-system.service.gov.uk/components/pagination/)

### Inferences
- *(inference)* Carbon ("no padding between them") and Material 2 ("below the last row") attach the pager to the table. In a filled frame the pager can sit either right under the last row or at the frame's bottom edge. No system answers that, because none fills the frame.

### Gaps
- Not covered: whether a pager under a short last page should stay where it was (the umriss "does not jump" rule). None of the systems mentions it.

## 4. Empty state versus no results after a filter (d)

### Takeaway
The systems that cover this treat the two as different states with different wording and a different action. Cloudscape has "No [items]" with a create action, and "No matches" with "Clear filter". PatternFly has "No results found" with "Clear all filters". Polaris has "No {resources} found" with "Try changing the filters or search term". Carbon separates "No data" from "User action" empty states. They differ on the frame around the message. Carbon replaces the whole table, header and footer included. Cloudscape keeps sorting and pagination on a no-match. PatternFly and Polaris draw the message inside the table body under the column headers. Atlassian puts its empty view under the header.

### Cited Findings
- Cloudscape: "An empty state occurs when users haven't created a resource or have deleted all existing resources. A zero results state occurs when users have filtered and there are no matches." Empty: "No distributions" plus a secondary-button action. Zero results: "No matches" and "Use this text: Clear filter". "Always display a resource counter". "Don't use empty states for errors." — [empty states](https://cloudscape.design/patterns/general/empty-states/). "If there is no match after filtering, don't hide sorting and pagination if they are enabled." — [table usage](https://cloudscape.design/components/table/?tabId=usage)
- Carbon: there are three types, "No data empty states", "User action empty states" ("No results when searching") and "Error management empty states". "Empty states should replace the element that would ordinarily show. For example, an empty state for a table would replace the table and the column headers and footer should not be present … if you search for something and there are no results, any underlying content should be replaced by the empty state message." "If space is limited, use just text." On dashboards with many widgets, "an empty state that uses just text may be preferable." — [empty states pattern](https://carbondesignsystem.com/patterns/empty-states-pattern/) ([MDX](https://github.com/carbon-design-system/carbon-website/blob/main/src/pages/patterns/empty-states-pattern/index.mdx))
- Carbon for IBM Products Datagrid: `emptyStateType` is one of `'error' | 'noData' | 'notFound'`, default `'noData'` — [DatagridEmptyBody.tsx](https://github.com/carbon-design-system/ibm-products/blob/main/packages/ibm-products/src/components/Datagrid/Datagrid/DatagridEmptyBody.tsx)
- PatternFly: "No results empty states appear when the system doesn't find any data to show … Use the small empty state variation". The heading "No results found" (Do) is preferred to "Your search did not yield any results" (Don't), and the body "Adjust your filters and try again." "Don't include toolbars or filters in a full-page empty state because the user doesn't have any items to search or filter." "Use a small empty state inside tables, wizards, or modals." "Empty states inside a table, card, or wizard should always be horizontally and vertically centered on their background." — [empty state guidelines](https://github.com/patternfly/patternfly-org/blob/main/packages/documentation-site/patternfly-docs/content/components/empty-state/empty-state.md). The demo puts the empty state in a `Td colSpan={8}` under the kept header, with "No results found" and a "Clear all filters" link — [Table demos](https://github.com/patternfly/patternfly-react/blob/main/packages/react-table/src/demos/Table.md), [TableEmptyStateDefault.tsx](https://github.com/patternfly/patternfly-react/blob/main/packages/react-table/src/demos/examples/TableEmptyStateDefault.tsx)
- Polaris: with no items, IndexTable falls back to `EmptySearchResult` "No {resourceNamePlural} found" / "Try changing the filters or search term", `withIllustration`. A separate `emptyState` prop is for "when no resources exist yet" — [IndexTable.tsx](https://github.com/Shopify/polaris/blob/main/polaris-react/src/components/IndexTable/IndexTable.tsx), [en.json](https://github.com/Shopify/polaris/blob/main/polaris-react/locales/en.json), [index-table MDX](https://github.com/Shopify/polaris/blob/main/polaris.shopify.com/content/components/tables/index-table.mdx)
- Atlassian: "A general no-result state (such as no search results) might be more neutral, but still motivate by showing next steps." Narrow size: "Use this for empty states in containers smaller than the default width" (304 px against 464 px) — [empty state](https://atlassian.design/components/empty-state/usage). The dynamic table keeps the head and renders `emptyView` after the table — [npm package](https://www.npmjs.com/package/@atlaskit/dynamic-table), `stateless.js`
- Primer: "Communicate when the table has no data to show. Show a `Blankslate` component in place of the table" — [data table MDX](https://github.com/primer/design/blob/main/content/components/data-table.mdx)
- React Spectrum: "Use `renderEmptyState` to render placeholder content when the table is empty." The example text is "No results" — [TableView](https://react-spectrum.adobe.com/TableView)
- Not covered: Fluent v8/v9, Material 2, GOV.UK, SLDS (v1 page).

### Inferences
- *(inference)* umriss keeps its pager on a no-result page. That matches Cloudscape and contradicts Carbon. The two leaders are split, so either choice can be defended. In a filled frame, keeping header and pager (Cloudscape, PatternFly) gives the message a stable, centred home in the body, which is PatternFly's "horizontally and vertically centered".
- *(inference)* Nobody puts the empty or no-match message in a short blank strip. Each one centres a message with an action in the space the rows would have taken. That speaks for the body of a filled frame holding the message.

### Gaps
- Carbon gives no rule for the case where the table must keep its frame (dashboard widget) while replacing itself. Its dashboard advice is only about text versus illustration.

## 5. Loading: skeleton rows, spinner overlay, and does the table keep its height? (e)

### Takeaway
Skeleton rows have replaced the spinner as the first choice: in Cloudscape, Carbon, Primer, and Fluent v8 with its shimmer. The reasons given are structure and avoiding layout shift. The default skeleton count is a fixed number everywhere: Carbon 5, IBM Products Datagrid 3, Fluent shimmer 10, Primer 10. The exception is Cloudscape, which in July 2026 added `skeleton.totalRows: 'auto'`, a row count "calculated from the available viewport height". Spinners remain for reloads over existing rows (Atlassian overlays the current page at 0.2 opacity; Material 2 uses a scrim with a linear progress bar) and for "load more" in nested rows (Cloudscape). An empty table that is loading gets a fixed-height box: Atlassian 9rem, PatternFly a single "Loading" row.

### Cited Findings
- Cloudscape: "For tables, use skeleton loading to display placeholder rows that match the table's column layout. Use a spinner to indicate progressive loading or loading of expandable rows." — [table usage](https://cloudscape.design/components/table/?tabId=usage). "A spinner can also be used in a table to indicate loading. However, we recommend using skeleton loading instead, as a spinner provides no structural context and can increase perceived loading time and layout shift." On refresh, "Keep the dataset visible while the refresh operation is ongoing" — [loading and refreshing](https://cloudscape.design/patterns/general/loading-and-refreshing/). "Don't animate or change skeleton dimensions while loading." — [skeleton](https://cloudscape.design/components/skeleton/?tabId=usage)
- Cloudscape Table `skeleton` prop: "`totalRows` (number) - The total number of rows that should be rendered. ### Inferences
- *(inference)* Cloudscape's `'auto'` skeleton is the closest any system comes to option (1). It measures the frame and fills it with exactly as many rows as fit. But it does this only for placeholders, and never for page size. For umriss it shows that a major system accepts "count rows from height" for the *loading* look of a filled frame. It also shows they kept the pager's page size out of it.
- *(inference)* Fluent fades the shimmer out at the bottom rather than ending it hard. That is a deliberate visual signal that the rows are not a count. It would also be a possible treatment for any placeholder rows in a filled frame.

### Gaps
- Not covered: how many skeleton rows Cloudscape shows when `skeleton` is not set (the fallback is its loading text). Whether Polaris' loading panel keeps the body's height. GOV.UK and Spectrum guidelines on loading.

## 6. Tables in fixed-height containers, cards and dashboard widgets (f)

### Takeaway
Three patterns appear. (1) **Top N plus "View all"**, with no pager inside the widget: Cloudscape's dashboard guidance and its demo. (2) **Defined height, scroll the rest**: PatternFly's dashboard tutorial (about four items, then scroll), Cloudscape's board items, which "introduce overflow", and Carbon's sticky-header table, capped at 300 px by default. (3) **Fill the parent and scroll inside**, used only by the virtualised, infinite-scroll grids: IBM Products Datagrid computes its body height from the parent, `lightning-datatable` is `height: 100%` of its parent, and in a frame that is too tall it keeps loading until it overflows. React Spectrum's examples give the table an explicit height. Cloudscape adds that resizing a dashboard item should "Show more or less content in rows or columns within a table". That is more rows through height, not through a page size. Carbon advises against tables in "smaller containers" altogether.

### Cited Findings

For example: when using a table in a dashboard item, expandable section, modal or within a split panel." / footer "for a View all link that navigates a user to a new page where they can view the complete items list" / "Don't expand a table after activating a View all footer link. Instead, navigate to a separate page with the full list of items." — [table usage](https://cloudscape.design/components/table/?tabId=usage)
- Cloudscape (dashboard items): "Avoid displaying long lists of data such as logs." / "use a details page for complex filtering on a table or a graph instead of on a dashboard" / footer "View all link that takes the user to a new page with the complete resource list." Configurable: The height of dashboard items has predefined height increments based on the grid." / Medium size example: "A table listing current alarms that need user intervention." — [dashboard items](https://cloudscape.design/patterns/general/service-dashboard/dashboard-items/)
- Cloudscape (board item): "Tables - Display a collection of items in a tabular format. ### Inferences
- *(inference)* For a paginated table in a widget, the system with the most dashboard guidance (Cloudscape) avoids the problem: no pager in the widget, a count in the header, top N rows, "View all". PatternFly picks "defined height + scroll". Neither draws a pager inside a card. That supports option (2), with the frame-filling table being the scrolling one, and a widget table not paginating at all.
- *(inference)* Cloudscape's "resize → more or fewer rows" is the user-facing intent behind option (1). In Cloudscape it comes from the frame's height plus overflow scrolling, not from a page size that follows the frame.
- *(inference)* IBM Products subtracts 48 px for a pager inside its fill-the-parent calculation. So one shipped grid does fill the parent *and* allow a pager. That is the case the owner objected to, and nothing in its docs shows how a page of 10 rows looks in a tall frame.

### Gaps
- No system says what to draw below a page of 10 rows in a frame that is taller than 10 rows.
- Cloudscape's board guidance on height ("predefined height increments", "select the height that best fits the content") does not say whether the table stretches inside a taller item. I did not render the demo to check.

## 7. Blank space, filler or empty rows under the last row (g)

### Takeaway
No design system draws empty ruled rows under the data. None prescribes a filler. The guidance that comes closest points the other way: PatternFly calls the leftover area in a dashboard "a gap of unused space" to be designed away (by matching heights or a defined height with scroll). Carbon puts empty states "in the otherwise empty space". Cloudscape draws placeholder rows after real rows only while loading (`totalRows - items.length`). Spreadsheets are the one place where ruled empty rows are normal. There the lines are the editing canvas: Excel "Gridlines are used to distinguish cells", and they are not printed by default. In Airtable the space under the last record is a creation affordance. The official guide describes "the plus sign at the bottom of a grid view", and a community answer says "This is default Airtable behavior to create a new record when clicking on the space immediately below the last record", with users deleting "meaningless records" as a result.

### Cited Findings
- PatternFly: "avoid situations such as having a one column dynamic card expand and push down a two column card below it, creating a gap of unused space" — [dashboard md](https://github.com/patternfly/patternfly-org/blob/main/packages/documentation-site/patternfly-docs/content/patterns/dashboard/dashboard.md)
- Carbon: "Empty states always appear in the otherwise empty space, in the context of the data that's missing. They can occur anywhere your app can display data, including but not limited to dashboards, data tables, tiles, full pages, and side panels." — [empty states MDX](https://github.com/carbon-design-system/carbon-website/blob/main/src/pages/patterns/empty-states-pattern/index.mdx)
- Cloudscape: skeleton rows can follow real items (`totalRows - items.length additional skeleton rows rendered after`) during loading only — [interfaces.tsx](https://github.com/cloudscape-design/components/blob/main/src/table/interfaces.tsx)
- Cloudscape and Spectrum each use a dash for an empty *cell*: "Use hyphen (-) for any empty values." — [table usage](https://cloudscape.design/components/table/?tabId=usage); "Use an en dash (–) for missing values" — [usage guidelines](https://spectrum.adobe.com/fragments/components/table/usage-guidelines). Primer says the opposite: "By default, leave empty cells blank … Just don't use a character like 'x' or '-'" — [data table MDX](https://github.com/primer/design/blob/main/content/components/data-table.mdx)
- Excel: "Gridlines are the faint lines that appear between cells on a worksheet." / "Gridlines are used to distinguish cells on a worksheet." / "Gridlines do not print by default." — [Microsoft Support](https://support.microsoft.com/en-us/office/show-or-hide-gridlines-on-a-worksheet-3ef5aacb-4539-4ad5-9945-5ed53772dc4d)
- Airtable: "You can manually add a record by selecting the plus sign at the bottom of a grid view, or with the shortcut shift + return." — [Airtable guide](https://www.airtable.com/guides/build/add-data-with-records). Community (no staff label, 2019-12-20): "This is default Airtable behavior to create a new record when clicking on the space immediately below the last record." / the asker: "So we have to live with it and on regular basis get rid if the meaningless records by deleting them." / accepted answer: "train yourself to avoid clicking in that space unless you want to make a new record." — [Airtable community](https://community.airtable.com/other-questions-13/automatic-new-created-record-after-clicking-in-any-field-below-last-record-16407). A later change made a click on the "ghost row" only deselect a selected cell [S] (search summary of the same forum)
- Fluent v8's shimmer placeholder rows fade out at the bottom to show "the unknown number of items" — [ShimmeredDetailsList.types.ts](https://github.com/microsoft/fluentui/blob/master/packages/react/src/components/DetailsList/ShimmeredDetailsList.types.ts)

### Inferences
- *(inference)* Empty ruled rows (option 3) carry a meaning in the tools users know, and it is "you can type or create here". Excel's lines mark editable cells. Airtable's space under the last row creates a record when clicked, and users complain about it. A read-only umriss table that draws rows it cannot fill would borrow that promise falsely. The evidence supports rejecting option (3).
- *(inference)* The systems treat leftover space as a layout problem: change the frame (PatternFly), centre a message in it (Carbon, PatternFly), or don't create it (Cloudscape: height defined by content in static dashboards). That points to the frame adapting, or the empty body carrying a message, and away from drawn filler.

### Gaps
- Google Sheets: Google's own help on sheet gridlines was not found. Only third-party how-tos came up (View > Show > Gridlines) [S] — [howtogeek](https://www.howtogeek.com/713062/how-to-hide-gridlines-in-google-sheets/)
- No system addresses a "short last page leaves blank space" case directly.

## 8. Row density and how it interacts with height (h)

### Takeaway
Every system offers two to five densities, roughly 24 to 64 px per row. Two systems tie density to the amount of data shown: PatternFly ("If you need to make more rows visible at a time, or if you don't want to use pagination, you can make your table compact") and Spectrum ("Use compact when fitting more data in a limited viewport is critical (e.g., dashboards…)"). Cloudscape makes density a stored user preference, comfortable by default. It should not be offered if the app has a global density switch.

### Cited Findings
- Carbon: "Data table header and row heights are available in five sizes": xs 24, sm 32, md 40 (default), lg 48, xl 64 px — [data table usage](https://carbondesignsystem.com/components/data-table/usage/); "The column header row … should always match the row size of the table. Extra large row heights are only recommended if your data is expected to have 2 lines of content in a single row." The tall toolbar goes with lg and xl, the small toolbar with sm and xs — [data table MDX](https://github.com/carbon-design-system/carbon-website/blob/main/src/pages/components/data-table/usage.mdx)
- Fluent v9 Table: `medium` 44 px, `small` 34 px, `extra-small` 24 px (cell `height`/`minHeight`) — [useTableCellStyles.styles.ts](https://github.com/microsoft/fluentui/blob/master/packages/react-components/react-table/library/src/components/TableCell/useTableCellStyles.styles.ts); Fluent v8 DetailsList `rowHeight: 42`, `compactRowHeight: 32` — [DetailsRow.styles.ts](https://github.com/microsoft/fluentui/blob/master/packages/react/src/components/DetailsList/DetailsRow.styles.ts)
- PatternFly: "Compact table: Use when you want to show as much data per page as possible." / "If you need to make more rows visible at a time, or if you don't want to use pagination, you can make your table compact." Use compact when "You need to show data in a small space" and "You need to minimize paging"; with default spacing, "You will need pagination to see more rows." — [table md](https://github.com/patternfly/patternfly-org/blob/main/packages/documentation-site/patternfly-docs/content/components/table/table.md)
- Cloudscape: content density "helps increase the visibility of large amounts of data" / "Set the content density preference to comfortable by default." / "Don't use the content density preference feature if your application already has a global density mode switch." — [table usage](https://cloudscape.design/components/table/?tabId=usage); preference toggles `contentDensity` "to display the data in a denser, more compact mode." — [collection preferences](https://cloudscape.design/components/collection-preferences/?tabId=usage)
- Spectrum: three densities (compact, regular, spacious) that change vertical padding, plus three sizes (s, m, l) that change font and spacing. "Use compact when fitting more data in a limited viewport is critical (e.g., dashboards, data-heavy admin panels)." / "Use small in constrained spaces or when the table is secondary" — [option details](https://spectrum.adobe.com/fragments/components/table/option-details); React Spectrum `density` default `'regular'` — [TableView](https://react-spectrum.adobe.com/TableView)
- Primer: "Condensed: Optimize for showing more information in a smaller area." / "Normal (default)" / "Spacious: Optimizes readability for tables with visually busy cell content." — [data table MDX](https://github.com/primer/design/blob/main/content/components/data-table.mdx); cell block padding 0.25 / 0.5 / 0.75 rem — [Table.module.css](https://github.com/primer/react/blob/main/packages/react/src/DataTable/Table.module.css)
- Material 2: "The baseline row height is 52dp, and the column header row height is 56dp" — [M2 archived](https://web.archive.org/web/20190528005308/https://material.io/design/components/data-tables.html)
- Airtable grid: four row heights, "Short (the most dense option, and the default height for new views)", Medium, Tall, "Extra Tall" — [grid view](https://support.airtable.com/docs/airtable-grid-view)
- GOV.UK: only `govuk-table--small-text-until-tablet` for tables with a lot of data — [table](https://design-system.service.gov.uk/components/table/)
- Not covered: Atlassian (no density), Polaris (`condensed` concerns small screens and bulk actions, not row height — [index-table MDX](https://github.com/Shopify/polaris/blob/main/polaris.shopify.com/content/components/tables/index-table.mdx)).

### Inferences
- *(inference)* umriss's touch-compact pitch (35 px) is in the same range as Fluent small (34) and Carbon sm (32), and its regular pitch (36) sits between Carbon md (40) and sm. No system changes row height to fill a frame. Density is a choice made by the user or the team, not derived from the layout.
- *(inference)* PatternFly's "compact = fewer pages" rule makes the link explicit: with a fixed frame, rows that fit = frame height / row pitch. If umriss ever ties page size to height (option 1), a density change would also change the page size. That is one more source of pages that shift.

### Gaps
- Material 3 has no data table to compare. The `material-web` docs list no table component, and its roadmap lists "Data table" under components "we have not built yet", with "No future work is planned while MWC is in maintenance mode" — [docs/components](https://github.com/material-components/material-web/tree/main/docs/components), [roadmap](https://github.com/material-components/material-web/blob/main/docs/roadmap.md). The m3.material.io component list itself would not render, so this is confirmed only through the library.
