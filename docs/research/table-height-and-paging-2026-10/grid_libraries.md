## 1. AG Grid `paginationAutoPageSize`: how is the page size computed, and what happens on resize, with the selector, with other row models?

### Takeaway
AG Grid divides the body height by **one** row height and takes the floor: `Math.floor(bodyHeight / rowHeight)`. The body height leaves out the header, the pinned top and bottom rows and the horizontal scrollbar. Variable heights are ignored. The page size is recomputed when the body height or scrollbar visibility changes, after a first synchronous pass and then through a 50 ms debounce. When auto is on, the page-size selector is hidden, and `paginationPageSize` and `paginationPageSizeSelector` are ignored. A resize keeps the **page index** (clamped) rather than the first visible row. The Infinite and Server-Side Row Models support it. Their requests go by block (`cacheBlockSize`), not by page, so a resize alone does not send a request. AG Grid calls this setup "the recommended approach" for the Infinite model.

### Inferences
- Because the result is floored, a page never holds half a row. The rest of the body height (less than one row) stays blank under the last row of every full page.
- A resize keeps the page index, so the first visible row moves. For example, page 3 at 10 rows/page shows rows 31–40; after the pane grows to 15 rows/page, page 3 shows rows 46–60. The user loses their place. TanStack keeps the top row instead (§8).
- Nothing in the listeners reacts to a change of `rowHeight` alone (`bodyHeightChanged`, `scrollVisibilityChanged` and the auto option only). A density change that keeps the body height would therefore not recompute the page size until the next resize. I read the listeners but did not run this.
- A short last page, a filter with few matches, or 0 rows still leaves blank body under the rows. Auto page size only removes the gap on full pages.

### Gaps
- `domLayout: 'autoHeight'` combined with `paginationAutoPageSize`: neither the docs nor the validation rules mention it. Under autoHeight the body height follows the rows (minimum 150 px), so the two feed each other. I did not test what page size results.
- Full-width rows and pinned rows inside the page: pinned rows are subtracted from the body height (above). Full-width rows count as ordinary rows of `rowHeight`, which I did not verify in source.

## 2. AG Grid `domLayout`: what fills the frame, what stands under the last row, overlays and the pagination panel

### Takeaway
In `normal` layout the grid fills the div it is given, and the docs openly say this leaves "empty space between the last row and the bottom of the grid" when there are few rows. `autoHeight` is AG Grid's answer to that, with a 150 px minimum body. The no-rows and no-matching-rows overlays are separate and centred over the body. Loading shows an overlay; optional skeleton rows come in a fixed count of 10 and do not fill the viewport. One documented example stretches the row height to fill a tall grid: a fourth option beside the three under discussion.

## 3. AG Grid: user reports and wishes around auto page size

### Takeaway
AG Grid's public GitHub tracker is thin, because support runs through Zendesk. The reports that exist are about wanting "Auto" as an entry in the page-size selector, scrollbar flicker with auto plus row groups, races with `paginationGoToLastPage`, the scrollbar being counted twice, and parents without a definite height. There is no report about density changes.

### Cited Findings
- Feature request: "The ability to add 'Auto' and 'All' to the paginationPageSizeSelector array … 'Auto' would be the same as setting 'paginationAutoPageSize: true' … Both options would leave the pagination control active on the screen, so that the drop-down selector was available." - `paginationGoToLastPage()` goes to the wrong page with auto, because of a race between setting data and computing the size. The workaround is a `setTimeout` — [#6047](https://github.com/ag-grid/ag-grid/issues/6047) (2023-01-20)
- The horizontal scrollbar was subtracted twice in `checkPageSize` — [#2979](https://github.com/ag-grid/ag-grid/issues/2979) (2019)
- Auto page size inside a wrapper without height "is continuously adjusted/calculated causing persistent rendering issues". - #9319 shows at least one licensed customer wanting auto to be **a choice in the selector**, next to fixed sizes. AG Grid does not offer this; it treats auto and the selector as mutually exclusive.

## 4. MUI X Data Grid `autoPageSize`: computation, selector, resize, server mode

### Takeaway
MUI X does the same as AG Grid: `Math.max(1, Math.floor(viewportInnerSize.height / rowHeight))`, where `rowHeight = rowHeight prop × density factor`. Density changes do recompute; variable and dynamic heights do not count. The "Rows per page" select is hidden by passing it no options. The page index is kept on resize (clamped). Every recomputed size goes through `setPaginationModel`, so with `paginationMode="server"` each resize step that changes the size fires `onPaginationModelChange`. Before the first measurement the page size is 0. `autoPageSize` and `autoHeight` together are rejected with a warning.

### Cited Findings
- Docs: "Use the `autoPageSize` prop to auto-scale the `pageSize` to match the container height and the max number of rows that can be displayed without a vertical scroll bar." Warning: "You cannot use both the `autoPageSize` and `autoHeight` props at the same time because `autoHeight` scales the height of the Data Grid according to the `pageSize`." — [pagination.md L52-L58](https://github.com/mui/mui-x/blob/d2408edc83af5aeaf582bc7cc6d8a022f5c5b734/docs/data/data-grid/pagination/pagination.md#L52-L58), [public page](https://mui.com/x/react-data-grid/pagination/#automatic-page-size). The same text is raised at runtime by a prop validator: "`<DataGrid autoPageSize={true} autoHeight={true} />` are not valid props." — [propValidation.ts L9-L18](https://github.com/mui/mui-x/blob/d2408edc83af5aeaf582bc7cc6d8a022f5c5b734/packages/x-data-grid/src/internals/utils/propValidation.ts#L9-L18)
- API description: "If `true`, the pageSize is calculated according to the container size and the max number of rows to avoid rendering a vertical scroll bar." — [data-grid.json](https://github.com/mui/mui-x/blob/d2408edc83af5aeaf582bc7cc6d8a022f5c5b734/docs/translations/api-docs/data-grid/data-grid/data-grid.json)
- Implementation: `const rowHeight = Math.floor(props.rowHeight * densityFactor)`; `handleUpdateAutoPageSize` computes `Math.max(1, Math.floor(dimensions.viewportInnerSize.height / rowHeight))` and calls `apiRef.current.setPageSize(…)`. It is wired to the `viewportInnerSizeChange` event and to an effect that depends on `rowHeight` — [useGridPaginationModel.ts L80, L233-L246, L314, L366](https://github.com/mui/mui-x/blob/d2408edc83af5aeaf582bc7cc6d8a022f5c5b734/packages/x-data-grid/src/hooks/features/pagination/useGridPaginationModel.ts#L233-L246). ## 5. MUI X `autoHeight`, flex parent and fixed parent: what fills, what stands under the last row, overlays and skeleton

### Takeaway
The MUI X grid "has no intrinsic dimensions" and "fills the space of its parent container". In a fixed-height parent, the body under the last row stays blank; one filler draws a closing border line under the last row (and reserves the horizontal-scrollbar height). `autoHeight` was deprecated in 7.19.0 in favour of a **flex parent** (`flex-direction: column`, optional min/max height) and **undeprecated in 8.19.0**. Both now stand side by side with "when to use" guidance, and a new `height` prop exists. "No rows" and "No results" are separate overlays. The loading **skeleton fills the viewport** with `Math.ceil(viewportHeight / rowHeight)` placeholder rows, unlike AG Grid's fixed 10.

## 6. MUI X: user reports around `autoPageSize`

### Takeaway
The reports concern dynamic and variable row heights (unsupported by design), jitter and flicker from scrollbar oscillation during container resizes, the page size of 0 before measurement in server mode, and a request to size the grid in **whole rows** so no partial-row gap remains below the last row. A maintainer posted a CSS recipe for that in 2026-09.

### Cited Findings
- "Is it possible to use dynamic row height with autoPageSize?": "the `autoPageSize` does not account for dynamic row height". Maintainer (2022): "I don't think we can support it properly. A specific page may have more rows than another page. This will make too confusing to use the pagination controls." Closing note (2026-09-11): "Supporting it would make the page size change as rows are measured, which would produce a different row count per page and confusing pagination … consider a fixed `pageSize` or the flex parent layout instead." — [#5697](https://github.com/mui/mui-x/issues/5697) (+1, c5). The closing note says the row-height page "now carries a warning". I found no such warning in [row-height.md](https://github.com/mui/mui-x/blob/d2408edc83af5aeaf582bc7cc6d8a022f5c5b734/docs/data/data-grid/row-height/row-height.md) at today's `master`
- "Allow for expressing the grid height in number of visible rows … To avoid a small space underneath the last row. This would play well with the `autoPageSize` property … `autoHeight` together with pagination is not enough as it can't account for height during loading, or for fewer items on the last page." Maintainer workaround (2026-09-09): `autoPageSize` plus `.MuiDataGrid-main { flexGrow: 0; height: calc(var(--DataGrid-topContainerHeight) + N * var(--height) + var(--DataGrid-bottomContainerHeight) + var(--DataGrid-hasScrollX) * var(--DataGrid-scrollbarSize)) }`, which "shows exactly N rows. The height stays stable during loading and on short last pages … with no leftover space". On variable heights: "'fixed height' and 'exactly N rows of unknown height' are contradictory requirements". Closed 2026-09-17 — [#13143](https://github.com/mui/mui-x/issues/13143)
- "flex columns jitter on container height change if using autoPageSize" (2023): "The dimension update subtracts the scrollbar width when the vertical scrollbar toggles, and the flex column widths recompute with the reduced viewport". Reported fixed by v9.12 after the scrollbar-oscillation detector in v9.3.0 (#22512) — [#11207](https://github.com/mui/mui-x/issues/11207) (c12)
- Early bugs from the 2021 rewrite: "autoPageSize still shows a small vertical scrollbar" [#1144](https://github.com/mui/mui-x/issues/1144); "AutoPageSize not resizing properly" [#1492](https://github.com/mui/mui-x/issues/1492); "Page size does not reset after clearing a filter when using `autoPageSize`" (a filter to 1 row left "100 pages with a page size of 1") [#1413](https://github.com/mui/mui-x/issues/1413); "No rendering with autoHeight + autoPageSize" [#3233](https://github.com/mui/mui-x/issues/3233)
- Server-side page size 0 — [#12936](https://github.com/mui/mui-x/issues/12936) (see §4)

### Inferences
- #13143 is the umriss owner's complaint seen from the other side: a frame that is not a whole number of rows leaves "a small space underneath the last row". MUI's answer is to **size the frame to N whole rows**, not to fill an arbitrary frame. That fits a dashboard widget, whose height umriss could round to rows, less well than a pane the user drags.

## 8. TanStack Table and TanStack Virtual

### Takeaway
TanStack Table is headless: no layout, no fit-to-height, no `autoPageSize` (zero code hits in the repo). The default page size is 10. One detail matters for umriss: `setPageSize` **keeps the current top row** and recomputes `pageIndex = floor(topRowIndex / newPageSize)`. - Keeping the top row is the better behaviour for "page size follows height" (option 1). The user's first visible row stays first, or at least on the current page, through every resize. umriss should copy it if it adopts option 1.
- react-table v6's padding rows are the one primary-source precedent for option (3), ruled empty rows to `pageSize`. Its own README calls the alternative "strange"; the library later removed layout altogether, which says little about users either way. I found no v6 issue praising or attacking the padding rows themselves.

### Gaps
- I did not search react-table v6 issues for complaints about the padding rows looking clickable.

## 9. React Spectrum TableView and React Aria Table

### Takeaway
React Spectrum's TableView is designed to **fill a layout-given height and scroll internally**. There is **no pagination at all**: the model is infinite scroll (`onLoadMore`, plus a centred spinner row for `loadingMore`). In S2, `TableFooter` holds summary rows, not a pager. With rows and no height, S2 TableView sizes to its content. When empty, the body is made as tall as the viewport and the empty state (`renderEmptyState`) is centred in it, but an empty table with **no** explicit height collapses to zero. An open 2026 issue asks to fix that, and its reporter names the blank-surface problem directly. React Aria's Table is unstyled and unvirtualized by default; with `Virtualizer` + `TableLayout` it needs a sized scroll container. I found no Spectrum design guidance on height, paging or empty tables.

### Inferences
- Adobe treats "a table in a pane" as a scroll surface without pages. Under few rows it shows blank body; with no rows it shows a centred message in the full body. This matches umriss option (2): paginated tables do not fill, scrolling tables do.
- `renderEmptyState` is one slot. "No data" versus "no match" is left to the app; Spectrum does not offer two built-in states as AG Grid and MUI X do.

## Summary for the design question

| | AG Grid | MUI X Data Grid | Material Table | TanStack | React Spectrum / Aria |
|---|---|---|---|---|---|
| Fills a frame of definite height? | Yes, `normal` layout fills the div; `autoHeight` shrinks to rows (150 px min body) | Yes by default; flex parent (min/max), `autoHeight` or `height` prop as alternatives | No, sizes to rows | Headless; virtualizer needs a sized scroll element | Yes, designed to fill a layout-given height and scroll |
| Auto page size? | `paginationAutoPageSize`: `floor(bodyHeight / rowHeight)`, 50 ms debounce | `autoPageSize`: `max(1, floor(viewportInner / (rowHeight × density)))`, 60 ms throttle | No | No (but `setPageSize` keeps the top row) | No pagination at all; infinite scroll |
| Variable row heights with auto | Ignored; "rows will not fit perfectly" | Unsupported by design (#5697) | n/a | n/a | n/a |
| Page after a resize | Page index kept, clamped (first row moves) | Page index kept, clamped (first row moves) | n/a | Top row kept | n/a |
| What stands under the last row | Blank body (docs: "empty space between the last row and the bottom") | Blank body plus one closing border line (filler) | Demo: one blank padding row of `53 × emptyRows` on short last pages (page > 0) | Your markup; v6 drew empty padding rows to `pageSize` | Blank body; empty state centred in full body |
| Page-size selector with auto | Hidden; `paginationPageSizeSelector` ignored; an "Auto" entry requested (#9319, backlog AG-12622) | Hidden (empty options) | n/a | n/a | n/a |
| Server mode with auto | SSRM/Infinite supported; fetch by block, so no request per resize ("recommended") | Each size change → `onPaginationModelChange`; page size 0 before measurement (#12936) | n/a | Manual | n/a |
| Empty vs no-match states | Two overlays: "No Rows To Show" / "No Matching Rows" | Two overlays: "No rows" / "No results found." | Your markup | Your markup | One `renderEmptyState`; app decides |
| Loading | Overlay; optional 10 skeleton rows | Skeleton fills viewport (`ceil(h / rowHeight)` rows) when empty; linear progress when rows exist | Your markup | Your markup | Centred spinner; spinner row for load-more |

Points for the three options:
- **Option 1 (page size follows height)** is what AG Grid and MUI X ship, with the same limits: one fixed row height, the selector hidden, floor rounding (a leftover strip under up to one row), and blank space on short last pages and filtered pages. Both keep the page index on resize; TanStack's "keep the top row" rule is the better model to copy. A server-backed table needs fetching by block or debounced, which AG Grid has and MUI X does not.
- **Option 2 (only scrolling tables fill)** is React Spectrum's whole model: no pager, fill and scroll, centred empty state. MUI X's #13143 and Spectrum's #10235 both show users disliking a fixed frame that leaves blank space under few rows.
- **Option 3 (ruled empty rows)** has one precedent, react-table v6's default padding rows, since dropped. Today ruled placeholders appear only as the animated loading skeleton (MUI X), never as an inert resting state.
- **Option 4, not on the list:** AG Grid's documented "Dynamic Vertical Resizing" stretches the row height so few rows fill the frame (application code, not built in). **Option 5:** MUI's maintainer recipe sizes the frame to exactly N whole rows (#13143), which removes the leftover strip but only where the frame can be chosen.
