## 1. `sap.ui.table.Table`: how do the row modes size the table, and what fills row slots that have no data?

### Takeaway
In `sap.ui.table` a "row" is a fixed-height slot in a virtual viewport, not a page. `Auto` is the mode that fills its frame: it measures the parent and shows `floor(availableSpace / rowHeight)` slots, never fewer than `minRowCount` (default 5). It checks the size by polling every 200 ms, throttled to one animation frame, and ignores changes under 5 px. When there are fewer data rows than slots, the leftover slots are **rendered as empty rows**: the cells keep their right and bottom borders, their content is hidden, and the row cannot be selected. The table's own doc calls this "a grid of empty cells". This is the umriss draft's option (3), and it is SAP's default. The only other choice, `hideEmptyRows`, is private to `sap.ui.mdc.Table`. It replaces the empty slots with one blank placeholder of the same height, which is umriss's present blank filler. The old `visibleRowCountMode`/`visibleRowCount`/`minAutoRowCount` properties have been deprecated since 1.119 in favour of the `rowMode` aggregation, which takes `Fixed`, `Auto` or `Interactive`.

### Inferences
- SAP's answer to "fill the frame whatever the row count" is count-follows-height on a **scrolling** viewport, with ruled, inert empty slots below the data. The owner fears exactly this (option 3) because the slots "look like clickable rows". SAP limits the problem in three ways: empty rows are never selectable; they carry no content, so no checkbox and no row-action icons (the selector cell's children are hidden as well); and the table's container is the scroll viewport anyway. It does not remove the ruling.
- From the source I could not settle whether empty rows get the hover background. `_onHover` in [extensions/Pointer.js L462-L471](https://github.com/UI5/openui5/blob/master/src/sap.ui.table/src/sap/ui/table/extensions/Pointer.js#L462-L471) sets `sapUiTableRowHvr` on whatever row sits under the pointer, without an emptiness check, whenever the table is selectable or has `cellClick` listeners, and [base/Row.less L29-L37](https://github.com/UI5/openui5/blob/master/src/sap.ui.table/src/sap/ui/table/themes/base/Row.less#L29-L37) gives that class a hover background and `cursor: pointer`. If no other guard exists, empty rows do highlight on hover, which would make the "looks clickable" risk real. This needs a look at the running sample.
- `hideEmptyRows` + placeholder is what umriss does today: the same height, no lines. SAP keeps it private and uses it only next to the creation row. That hints SAP sees the blank-under-rows look as the exception, not the default.
- The 200 ms polling plus the 5 px dead band is how SAP avoids resize thrash and ResizeObserver loop errors. A ResizeObserver plus a hysteresis band would be the modern equivalent.

### Gaps
- I did not see the RowModes sample rendered ([Demo Kit sample](https://ui5.sap.com/#/entity/sap.ui.table.Table/sample/sap.ui.table.sample.RowModes)). So whether empty rows show hover, and how the stripes look, is inferred from source, not observed.

## 2. Did `sap.ui.table` have a paginator, and why was it removed?

### Takeaway
Yes. `navigationMode: "Paginator"` existed and was deprecated in 1.38. Today the setter forces `Scrollbar` and logs an error. SAP's reasoning, from a table developer on GitHub, is that the paginator is "a questionable UI pattern" and that a virtual scrollbar does the same job better: data is loaded per visible "page" anyway, and any position can be reached directly. SAP added that "There will be no Paginator control in sap.m".

### Cited Findings
- `NavigationMode.Paginator`: "Uses the paginator control. This option must no longer be used. Using a scrollbar is the only navigation mode which is supported by the `sap.ui.table` library. The `navigationMode` property has always been a visual representation. No matter which navigation mode is used, data fetched from an OData service is loaded page-wise." `@deprecated As of version 1.38` — [library.js L119-L140](https://github.com/UI5/openui5/blob/master/src/sap.ui.table/src/sap/ui/table/library.js#L119-L140)
- The property: "deprecated and must not be used anymore, since `Scrollbar` is the only supported option. @deprecated As of version 1.38, the concept has been discarded." — [Table.js L218-L223](https://github.com/UI5/openui5/blob/master/src/sap.ui.table/src/sap/ui/table/Table.js#L218-L223). The setter: `this.setProperty("navigationMode", "Scrollbar", true); Log.error("The navigationMode property is deprecated and must not be used anymore. Your setting was defaulted to 'Scrollbar'", this);` — [Table.js L2438-L2442](https://github.com/UI5/openui5/blob/master/src/sap.ui.table/src/sap/ui/table/Table.js#L2438-L2442)
- openui5 #1131 "sap.ui.table.NavigationMode and PaginatorControl -- why on Earth was it taken out?" (2016-09-02). SAP contributor thomaskoetter: "The underlying reason is that we need to clean up the table code to keep it maintainable. In the case of the paginator, we don't feel that anything is lost except for a questionable UI pattern. … if you use the scrollbar to go to entry 1.023.045, we will only load the data for the visible "page" at that point. This is not much different from a paginator, but has the added benefit that you can directly scroll to any page. With a paginator you can directly go to only a small number of pages." SAP contributor simlin (2017-07-20): "the paginator approach was removed as we do not want to follow this path further. There will be no Paginator control in sap.m". The reporter replied that "on desktop applications users prefer click actions to drag a scrollbar", and another user: "Scrolling is really difficult to use and the users hate it." — [#1131](https://github.com/UI5/openui5/issues/1131)

### Inferences
- SAP removed paging from its desktop grid and replaced it with scroll (grid table) or growing (responsive table, §3). Pushback from users exists, but there is not much of it: the issue was closed after a few comments.

### Gaps
- No Fiori-guideline text explicitly saying "do not paginate tables" could be read (site blocked). §3 has the related [S] snippets.

## 3. What do the SAP Fiori guidelines and Fiori elements prescribe: row count, growing, counts, empty states, cards?

### Takeaway
Fiori elements makes a grid table **fill its frame only when the table owns it**. It uses `Auto` when the table is the sole control of a section with tab layout, and otherwise a fixed 5 rows (10 for tree and analytical tables). The metadata-driven `sap.ui.mdc` grid table defaults to `Auto` with `rowCount` 10 as the minimum. For the responsive table SAP does not page. It "grows" by chunks of `growingThreshold` (default 20; 10 on an object page with several sections). A "More" button shows a `[ 20 / 250 ]` counter under its text, and the guideline snippets prefer scroll-to-load [S]. Empty tables get three different illustrated messages: before the first search, no entries at all, and no results for the filter. Integration cards are the one place SAP offers a paginator (experimental). There, `minItems` reserves height and the doc says outright that this leaves empty space.

## 4. DevExtreme DataGrid: paging, pager, height, and what stands under the last row

### Takeaway
DevExtreme pages by default (`paging.enabled` true, `pageSize` 20). It hides the pager when there is only one page (`pager.visible: 'auto'`). There is **no page-size-from-height feature**: `allowedPageSizes: 'auto'` means `[⌊pageSize/2⌋, pageSize, pageSize×2]`, not "as many as fit". What stands under the last row is a **free-space row** that works exactly like umriss's current filler. Without a `height`, on a short last page, it reserves `(pageSize − rows) × rowHeight`, so the pager does not move. With a `height`, it stretches to fill the rest of the grid. It has no row lines but carries the column cells (and so the column lines when `showColumnLines` is on).

## 5. Kendo UI Grid (jQuery) and KendoReact Grid: pageable, height and filling a parent

### Takeaway
Kendo is the only vendor in this scope that publishes the owner's option (1) as an **official knowledge-base recipe**: "Dynamically Change the Page Size of the Grid to Adjust Its Height". It measures header, pager and row heights on `window.resize` and sets `dataSource.pageSize(rows)`. It is a recipe, not a feature. It uses `scrollable: false`, runs only on window resize, and rounds rather than floors. Filling a parent is otherwise documented as `height: 100%` on the wrapper, all the way up the ancestor chain, plus a manual `resize()` call. By default the pager stays visible on a single page (`alwaysVisible: true`).

## 6. Ant Design Table and ProTable: `scroll.y`, pagination, and the requests to fill the parent

### Takeaway
`scroll.y` is a **max-height** on the body, so an antd Table never fills its frame, and the pager moves with the row count. That was a deliberate change in 2016, made because a user asked for it. Since then users have asked many times for the opposite: a fixed body height so "the pagination below does not jump" (#49445), "Fit parent height" (#23974, +40, and the maintainer's "won't implement" got 95 thumbs-down). In 2023 a core maintainer proposed `scroll.y = 'fill'`, then declined it on 2026-07-01 because measuring the parent in auto/flex layouts "can create a layout feedback loop". ProTable closed its "fill the content area" request as not planned on 2026-10-03. Pagination defaults: 10 per page, `[10, 20, 50, 100]`, the size changer appears automatically above 50 items, and the pager is shown even on a single page.

### Inferences
- antd lived through both sides of the owner's dilemma. First "no extra space" (max-height, 2016), then a steady stream of "keep the pager still / fill the parent" requests, which the maintainers still decline. The reaction counts suggest users want fill-the-frame more than a body sized to its content.
- zombieJ's feedback-loop objection is the key engineering point for umriss. Fill must only respond to a parent whose height does not depend on the table (a definite height). umriss already limits fill to "a parent of definite height", which is the condition he names.

## 7. Syncfusion Grid (optional): is there a built-in "page size from height"?

### Takeaway
Yes, as a public method. `grid.calculatePageSizeByParentHeight(containerHeight)` returns `floor((container − header − toolbar − pager − group area − summary rows) / rowHeight)`. It works only when rows cannot wrap, and the docs call the matching section "Dynamically calculate page size based on element height". The app still has to call it and set `pageSettings.pageSize`. It is not automatic.

### Cited Findings
- Source: `public calculatePageSizeByParentHeight(containerHeight: number | string): number`. It applies only `if (this.allowPaging)` and `if ((this.allowTextWrap && this.textWrapSettings.wrapMode === 'Header') || (!this.allowTextWrap))`, accepts `%` of the element height, and computes `pagesize = (contentHeight / this.getRowHeight()); … return Math.floor(pagesize);`, otherwise 0. `getNoncontentHeight()` adds the header, toolbar, pager, group drop area and summary rows — [controls/grids/src/grid/base/grid.ts L10300-L10345](https://github.com/syncfusion/ej2-javascript-ui-controls/blob/master/controls/grids/src/grid/base/grid.ts#L10300-L10345)
- Docs (Vue): "You have an option to dynamically calculate the page size of a grid by considering the height of its parent element." It "primarily serves the purpose of automatically adjusting the `pageSize` when the height of the grid's parent element changes dynamically", avoiding "any unwanted empty spaces within the grid". `pageSize` default **12**, `pageCount` default 8; the page-size dropdown defaults to `['All', '5', '10', '15', '20']` — [Syncfusion Vue Grid paging](https://ej2.syncfusion.com/vue/documentation/grid/paging.html) (read via the summarising fetch tool)
- Pager strings: `currentPageInfo: '{0} of {1} pages'`, `totalItemsInfo: '({0} items)'`, `All: 'All'`; `pageSize` `@Property(12)` — [controls/grids/src/pager/pager.ts L121-L122, L262-L283](https://github.com/syncfusion/ej2-javascript-ui-controls/blob/master/controls/grids/src/pager/pager.ts#L262-L283). Empty text: `EmptyRecord: 'No records to display'` — [grid.ts L3496](https://github.com/syncfusion/ej2-javascript-ui-controls/blob/master/controls/grids/src/grid/base/grid.ts#L3496)
- Support forum, 2019 [S]: a React user asks for a dynamic page size from height; support answers that the default row height is 37 px including the border and suggests recomputing on window resize — [forum 149820](https://www.syncfusion.com/forums/149820/set-dynamic-page-size-for-grid-based-on-the-grid-height) [S], [forum 154367](https://www.syncfusion.com/forums/154367/dynamically-calculating-the-number-of-rows-to-appear-depending-on-browser-windows-height) [S]

### Inferences
- Syncfusion's guard (only when rows cannot wrap) matches SAP Auto's "All rows need to have the same height". A fixed row pitch, which umriss already has, is the precondition every vendor names for option (1).

### Gaps
- I did not see the Syncfusion live demo, so I do not know how it behaves while the parent is being resized (debounce, current-page preservation).

Points that bear directly on the three options:
- **Option (1)** (page size follows height) exists as an API only in Syncfusion and as an official recipe in Kendo. Both require uniform row height and leave resize handling to the app. SAP does count-follows-height for a scrolling viewport, not for pages. DevExtreme's `'auto'` page sizes are not height-based.
- **Option (2)** (only scrolling tables fill) is close to SAP's position: SAP dropped paging from the grid table altogether, and its fill mode lives on the scroll viewport. Fiori elements narrows it further: fill only when the table owns the frame.
- **Option (3)** (ruled empty rows) is SAP's shipped default (Auto/Fixed without `hideEmptyRows`), made inert (not selectable, no content). Its hover state is unverified. DevExtreme instead pads with an unruled free-space row, which is umriss's current filler.
- The owner's objection ("10 rows and a big blank surface") is the reason antd switched to max-height in 2016. The opposite complaint (pager jumping, table not filling) has kept coming back since, and the maintainers gave the feedback-loop risk as the reason not to auto-measure.
