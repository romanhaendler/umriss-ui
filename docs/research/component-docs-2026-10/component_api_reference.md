# Component pages and API/props reference in UI library docs, state of the art (as of Oct 2026)

Method note: these findings come from fetching live docs pages and reading the docs-tooling source on GitHub (React Aria `packages/dev/s2-docs`, Base UI `docs/src/components/ReferenceTable`, MUI `packages-internal/api-docs-builder`, Mantine `@mantinex/demo`, Radix `website/components/props-table.tsx`). The WebFetch summarizer sometimes misses UI that only renders on the client (popovers, accordions, SVG diagrams). Where the page summary and the source disagree, the source is cited and the disagreement is noted.

## Page anatomy of component pages (sections, ordering, anatomy, when to use, a11y, styling API, related)

### Takeaway
Headless and primitive libraries (Radix, Base UI, Ark, Headless UI, React Aria) converge on one order: hero demo, then Anatomy (a code skeleton of the parts), then feature-oriented Examples, then a per-part API Reference that pairs each props table with its data-attributes and CSS-variables tables, then Accessibility and Keyboard. Design systems (Carbon, Primer, Atlassian) split the page into tabs (Usage or Guidelines / Code / Accessibility / Changelog). They put "when to use" guidance and numbered anatomy diagrams on the guidelines tab, and often push the props reference out to Storybook.

### Cited Findings

- ComboBox page order: hero example shown in two flavours ("Vanilla CSS example" with `ComboBox.tsx`/`ComboBox.css` file tabs, then "Tailwind example"), then feature sections Content › TagGroup, Value › Input value › Fully controlled, Item actions, Forms, Popover, then API. [React Aria ComboBox](https://react-aria.adobe.com/ComboBox)

[ComboBox.mdx](https://github.com/adobe/react-spectrum/blob/main/packages/dev/s2-docs/pages/react-aria/ComboBox.mdx), [pages dir](https://github.com/adobe/react-spectrum/tree/main/packages/dev/s2-docs/pages/react-aria). ### Inferences
- Read together, the headless-library pages suggest a canonical skeleton: one-line description, then a hero demo with editable controls, then Anatomy (a code skeleton or SVG of the parts), then one feature-named example section per concern (Content, Value, Selection, Forms, Overlay…), then an API Reference with a props table, a data-attributes table and a CSS-variables table per part, then Accessibility/Keyboard, then Related. The design-system "When to use / When not to use" and Do/Don't content sits on a separate guidelines tab.
- "Styling API" is a first-class table set everywhere in 2026: data attributes (Base UI, Radix, Ark, Headless UI), CSS variables (Base UI, Radix, Ark), slots/selectors (Mantine Styles API, MUI Slots + CSS classes, HeroUI `classNames`). This is where umriss's styling hooks belong.
- React Aria's feature section headings track its prop groups (Content, Value, Selection, Forms…). The example sections and the API groups share one vocabulary.

### Gaps
- Fluent UI 2: the Storybook docs (storybooks.fluentui.dev) did not render server-side, so I could not verify its page structure. Fluent v9's reference is Storybook-autodocs-based (ArgTypes + Controls), but the section order went unverified.
- I did not fetch a live Polaris web-components component page.
- I did not check React Aria's Accessibility/Keyboard sections on the new site. The fetched ComboBox page showed none, and the old site had them.

## Props tables: columns, grouping, search/filter, collapsible types, controlled/uncontrolled pairs

### Takeaway
Best in class are React Aria (props grouped into collapsible categories by name rules, a required asterisk, the description in a full-width row under each prop) and Base UI (each prop an accordion row that expands to Name/Description/Type/Default/Example, with a configured ordering that keeps `defaultX` / `x` / `onXChange` together and a deep-link anchor per prop). Most others use a flat 3–4-column table.

### Cited Findings
- **React Aria `PropTable.tsx`** groups props by a hard-coded `PROP_GROUPS` map. The groups are Content (`children`, `items`, `defaultItems`, `loadingState`, `onLoadMore`, `renderEmptyState`, …), Selection (`selectionMode`, `selectedKeys`, `defaultSelectedKeys`, `onSelectionChange`, `disabledKeys`, …), Value (`value`, `defaultValue`, `onChange`, `onChangeEnd`, `inputValue`, `defaultInputValue`, `onInputChange`, `formatOptions`), Labeling, Validation, Overlay (`isOpen`, `defaultOpen`, `onOpenChange`, `placement`, `offset`, …), Events (regex `/^on[A-Z]/`), Links, Styling (`style`, `className`), Forms, Accessibility (`autoFocus`, `role`, `id`, `tabIndex`, regex `/^aria-/`), and Advanced (`UNSAFE_className`, `UNSAFE_style`, `slot`, `render`). Each group renders as a `<DisclosureRow>`, with `DEFAULT_EXPANDED = new Set(['Content','Selection','Value'])`. The ungrouped core props stay visible at the top. [PropTable.tsx](https://github.com/adobe/react-spectrum/blob/main/packages/dev/s2-docs/src/PropTable.tsx)
- In the same file, each prop row has a name cell (`<code>` plus an `Asterisk` icon with `aria-label="Required"`), a Type cell (`<Type type={prop.value}/>`) and a Default cell ("—" if none, hidden on small screens when empty). The Markdown description goes in a second full-width row (`colSpan={3}`). Required asterisks show only when the component has a mix of optional and required props ("Default to showing required indicators if some properties are optional but not all"). [PropTable.tsx](https://github.com/adobe/react-spectrum/blob/main/packages/dev/s2-docs/src/PropTable.tsx)
- Live rows: `menuTrigger | MenuTriggerAction | 'input'`, `allowsCustomValue | boolean`, `onInputChange | (value: string) => void`, `children | ChildrenOrFunction<ComboBoxRenderProps>`. [React Aria ComboBox](https://react-aria.adobe.com/ComboBox)
- **Base UI `ReferenceAccordion.tsx`**: the header row has the columns Prop / Type / Default and an expand icon. Each prop is an `Accordion.Item` whose trigger shows the name (with a `<sup>*</sup>` when required), the *short* type and the default. Expanding it reveals a description list with **Name** (a self-link `#${part}-${name}`), **Description**, **Type** (the *detailed* type), **Default**, and **Example** (`prop.example`). The trigger's `aria-label` reads e.g. "Prop: value, required, type: … (default: …)". [ReferenceAccordion.tsx](https://github.com/mui/base-ui/blob/master/docs/src/components/ReferenceTable/ReferenceAccordion.tsx)
- **Base UI ordering config** (`typeOrder.mjs`) fixes the order of props (`aria-label`, `aria-labelledby`, `name`, `label`, `defaultChecked`, `checked`, `onCheckedChange`, `indeterminate`, `defaultValue`, …) and of data attributes (`data-checked`, `data-unchecked`, `data-open`, …, `__EVERYTHING_ELSE__`, `data-starting-style`, `data-ending-style`). The effect is that controlled/uncontrolled/handler triples always appear adjacent. [typeOrder.mjs](https://github.com/mui/base-ui/blob/master/docs/src/utils/typeOrder.mjs)
- Base UI live rows: `value | Value[] | Value | null | undefined`, `onValueChange | ((value: Value[] | Value | null, eventDetails: Select.Root.ChangeEventDetails) => void) | undefined`, `className | string | function`, `render | ReactElement | function`. [Base UI Select](https://base-ui.com/react/components/select)
- **MUI API page**: columns Name / Type / Default / Description, with required props marked by an asterisk. Defaults are explicit (`false`, `'medium'`, `-1`), deprecations are inline, and long types are not collapsible. [MUI Autocomplete API](https://mui.com/material-ui/api/autocomplete/)
- **Radix**: columns Prop / Type / Default ("No default value"). The description is *not* a column: it sits in a Popover behind an `InfoCircledIcon` next to the prop name. Required props get "*". [Radix props-table.tsx](https://github.com/radix-ui/website/blob/main/components/props-table.tsx)
- **Mantine Props tab**: name, type, default and required status, with descriptions taken from JSDoc. [Mantine Select props](https://mantine.dev/core/select/?t=props)
- **Atlassian**: Property / Description / Type. No required or default columns were visible. [Atlassian Select Code](https://atlassian.design/components/select/code)
- **Primer**: Name / Default / Description, with the union in the type position (`variant | 'default' | 'default' | 'primary' | 'danger' | 'invisible' | 'link'`). [Primer Button](https://primer.style/product/components/button/)
- **Headless UI**: Prop / Default / Description, with the type inline. Nested object props are flattened into dotted rows (`anchor`, `anchor.to`, `anchor.gap`, `anchor.offset`, `anchor.padding`). [Headless UI Listbox](https://headlessui.com/react/listbox)
- **Chakra v3**: Prop / Default / Type / Description per part, with `*` for required (`collection *`). [Chakra Select](https://chakra-ui.com/docs/components/select)
- **Storybook ArgTypes**: `table.category` and `table.subcategory` group rows under (sub)category headings, `table.type.{summary,detail}` and `table.defaultValue.{summary,detail}` separate the short form from the expandable detail, and `table.disable` hides a row. The `ArgTypes` doc block takes `include` / `exclude` (regex or array) and `sort: 'none' | 'alpha' | 'requiredFirst'`. [Storybook ArgTypes](https://storybook.js.org/docs/api/arg-types), [ArgTypes doc block](https://storybook.js.org/docs/api/doc-blocks/doc-block-argtypes)

### Inferences
- The strongest grouping model uses rules, not hand-curation: React Aria's name regexes (`/^on[A-Z]/` → Events, `/^aria-/` → Accessibility) plus explicit lists for domain groups. Inherited DOM or aria props then collapse into closed groups instead of drowning the component's own props.
- Controlled/uncontrolled triples are handled by *ordering and grouping* (React Aria's Value/Selection/Overlay groups; Base UI's ordering config), not by a dedicated "controlled" column. No library observed renders a merged "value / defaultValue / onChange" row.
- "since" and "deprecated" columns are rare. MUI inlines deprecations in the description, and Atlassian puts deprecation notices in the description. No library observed has a "since version" column.

### Gaps
- Within-page props search or filter: none of the fetched pages showed a dedicated props filter field. The Mantine fetch mentioned only the site-wide Ctrl+K search, so whether the Mantine Props tab has its own filter is unverified.
- I did not verify whether Base UI or React Aria list DOM-inherited props (e.g. `onClick`) explicitly or omit them.

## Type rendering: unions, named types, generics, callbacks, ReactNode, refs, links/popovers

### Takeaway
The state of the art is React Aria's own TS-AST renderer: every type kind is rendered as syntax-highlighted TS, unions longer than two members break onto new lines, and every named type is a link that opens a popover with its definition. Nested named types push breadcrumbs inside the same popover. Base UI comes close with short-type/detailed-type pairs, hover popovers (`TypeRef`) and "additional types" sections with anchors. MUI renders flat strings with a separate `Signature:` block and per-parameter descriptions taken from JSDoc `@param`/`@returns`. Radix hand-writes a `typeSimple` with an info popover holding the full type.

### Cited Findings
- **React Aria `types.tsx`** has a `Type` switch over the kinds `any/null/undefined/void/unknown/never`, `this`, `symbol`, `identifier`, `string`/`number`/`boolean` literals, `union`, `intersection`, `application` (generic instantiation `Foo<T>`), `typeOperator`, `function`, `parameter`, `link`, `interface`, `object`, `alias`, `array`, `tuple`, `typeParameter` (with `constraint` and `default`), `component`, `conditional`, `indexedAccess`, `keyof` and `template` literal. In other words it renders the real TS type AST, not a string. [types.tsx](https://github.com/adobe/react-spectrum/blob/main/packages/dev/s2-docs/src/types.tsx)
- Unions are rendered by `JoinList` with joiner `' | '`. Above two elements they always break onto new lines with indentation, and with two or fewer they indent only on small screens. `FunctionType` renders `name`, `typeParameters`, `parameters` (each `Parameter` with `optional`, `rest`, `default`) and `return`. [types.tsx](https://github.com/adobe/react-spectrum/blob/main/packages/dev/s2-docs/src/types.tsx)
- A named type renders through `LinkType` → `TypeLink` → `TypePopover`. The popover shows the type's JSDoc description (Markdown), an "Extends: …" line for interfaces, a "Props" heading for components, and the full interface/alias body. Types listed in `DOC_LINKS` (types with their own doc page) render as plain identifiers. [types.tsx](https://github.com/adobe/react-spectrum/blob/main/packages/dev/s2-docs/src/types.tsx)
- `TypePopover.tsx` ("Displays a link with a popover to browse a TypeScript type definition"): clicking a type link inside an open popover pushes it onto a breadcrumb stack within the same popover (`Breadcrumbs` for back-navigation) instead of nesting popovers. Max width is 600. [TypePopover.tsx](https://github.com/adobe/react-spectrum/blob/main/packages/dev/s2-docs/src/TypePopover.tsx)
- Live examples: `MenuTriggerAction` (a named alias, linked), `ChildrenOrFunction<ComboBoxRenderProps>` (generic application), `ValueType<M>`, `(value: string) => void`. [React Aria ComboBox](https://react-aria.adobe.com/ComboBox)
- **Base UI**: each prop carries `shortType` (shown collapsed) and `detailedType` (shown when expanded), produced by `@mui/internal-docs-infra/useTypes`. [ReferenceAccordion.tsx](https://github.com/mui/base-ui/blob/master/docs/src/components/ReferenceTable/ReferenceAccordion.tsx)
- Base UI `TypeRef`: "Renders a type reference as an interactive element. When clicked, displays a popover showing the type's documentation rendered via `ReferenceTable`". It is a `Popover.Trigger openOnHover`, guards against circular references (self-references render as a plain span), and falls back to an anchor link when no data exists. [TypeRef.tsx](https://github.com/mui/base-ui/blob/master/docs/src/components/TypeRef/TypeRef.tsx)
- Base UI `AdditionalTypes`: named auxiliary types (e.g. `Select.Root.ChangeEventDetails`, `Select.Positioner.State`) each get their own heading with an `id` slug and a formatted TS code block. A "Back"/"Hide" link returns to the referring prop, and re-exports say "Re-Export of X as Y". [AdditionalTypes.tsx](https://github.com/mui/base-ui/blob/master/docs/src/components/ReferenceTable/AdditionalTypes.tsx), [Base UI Select](https://base-ui.com/react/components/select)
- Base UI shows generics as the namespaced props type, `Select.Root.Props<Value, Multiple>`. [Base UI Select](https://base-ui.com/react/components/select)
- **MUI**: unions are pipe-separated (`'mouse' | 'touch' | bool`), and callbacks get "Signature: `function(event: React.SyntheticEvent, value: Value | Array<Value>, reason: string, details?: string) => void`" followed by a description of each parameter. `node` and `elementType` are PropTypes-style names. [MUI Autocomplete API](https://mui.com/material-ui/api/autocomplete/)
- MUI's builder (`generatePropDescription.ts`) builds the signature from JSDoc `@param {Type} name desc` and `@returns` tags, and resolves `@template` tags so it can describe generic arguments (`argType`, `argTypeDescription`). **It throws** `Function signature for prop '${propName}' has no return type. Try @returns void` and `In function signature for prop '${propName}' Argument #${index} has no type.` [generatePropDescription.ts](https://github.com/mui/material-ui/blob/master/packages-internal/api-docs-builder/src/utils/generatePropDescription.ts)
- **Radix**: the props data has both `type` and a hand-written `typeSimple`. The cell shows `typeSimple` (e.g. `enum`, `function`), and an `InfoCircledIcon` Popover reveals the full `type`. [props-table.tsx](https://github.com/radix-ui/website/blob/main/components/props-table.tsx)
- **Ark / Chakra** show TS syntax with generics, e.g. `onValueChange: (details: ValueChangeDetails<T>) => void`, `collection: ListCollection<T>`, `positioning: PositioningOptions`. The named type is unexpanded in the cell. [Ark Select](https://ark-ui.com/docs/components/select), [Chakra Select](https://chakra-ui.com/docs/components/select)
- **Headless UI** shows TS-like inline types: `value: T`, `onChange: (value: T) => void`, `by: keyof T | ((a: T, z: T) => boolean)`. [Headless UI Listbox](https://headlessui.com/react/listbox)
- **Atlassian** shows types as plain strings with no links or expansion, e.g. `readonly React.RefObject<HTMLElement>[]`. [Atlassian Select Code](https://atlassian.design/components/select/code)
- **react-docgen-typescript** options that govern type output: `shouldExtractLiteralValuesFromEnum` ("string enums and unions will be converted to docgen enum format"), `shouldExtractValuesFromUnion` ("every unions will be converted to docgen enum format"), `shouldSortUnions`, `shouldRemoveUndefinedFromOptional` ("types that are optional will not display ' | undefined'"), `savePropValueAsString`, `skipChildrenPropWithoutDoc` (default true), `propFilter`, `componentNameResolver`. [react-docgen-typescript](https://github.com/styleguidist/react-docgen-typescript)
- **Storybook**: types reach the table as `table.type.summary` (short) plus `table.type.detail` (long, expandable). React inference uses react-docgen (the default) or react-docgen-typescript. [Storybook ArgTypes](https://storybook.js.org/docs/api/arg-types)

### Inferences
- The minimum bar for "types cleanly stated and defined" in 2026: (1) render in TS syntax, never PropTypes words like `func`/`node`; (2) show a short form in the row with the full form one click away; (3) make every named type (callback-details objects, state objects, unions aliased as `XAction`) a link to a definition, whether a popover or an anchored "additional types" block; (4) break unions longer than two members onto new lines; (5) document callback parameters individually (MUI's per-`@param` text, or React Aria/Base UI's linked details types).
- With react-docgen-typescript, enable `shouldExtractLiteralValuesFromEnum` and `shouldRemoveUndefinedFromOptional` to get literal unions without the `| undefined` noise. It still returns string-ish types with no named-type graph. Linkable, expandable types need a TS-compiler/ts-morph-based extractor like React Aria's or MUI's `internal-docs-infra`.
- Neither Base UI (which prints `| undefined`) nor MUI strips `undefined` everywhere. React Aria shows `MenuTriggerAction | undefined` in the live table but not in source-level renders. This is cosmetic, but it adds noise.

### Gaps
- TypeDoc and API Extractor/api-documenter rendering of the same constructs was not fetched in detail this session. Only their validation features were verified (next sections).
- How `ReactNode` and `Ref` types render was not specifically observed, beyond MUI's `node` and Base UI's `ReactElement | function`.

## Per-prop examples: which libraries tie every prop to a demo, configurators/playgrounds, prop→example anchors

### Takeaway
No library *guarantees* a demo per prop by tooling. They get coverage in three ways. First, *interactive controls on the hero and feature demos*: React Aria's code fences declare `props={[...]}`, and the control widgets come from the prop types; Mantine's `configurator` demos list typed controls; Storybook generates Controls from argTypes. Second, *one doc heading per prop or feature* (Mantine, MUI). Third, a per-prop `@example` shown inside the prop's expanded row (Base UI).

### Cited Findings
- **React Aria**: examples are MDX code fences with metadata, e.g. ```` ```tsx render docs={vanillaDocs.exports.ComboBox} props={['label','selectionMode','isDisabled']} initialProps={{label:'Favorite Animal', placeholder:'Select an animal'}} ````. Per-feature fences expose the prop they teach: the "Input value" section has `props={['allowsCustomValue']}` and the Popover section has `props={['menuTrigger','allowsEmptyCollection']}`. Because `docs=` passes the extracted type info, the playground controls are typed from the same source as the props table. [ComboBox.mdx](https://github.com/adobe/react-spectrum/blob/main/packages/dev/s2-docs/pages/react-aria/ComboBox.mdx)
- The React Aria `VisualExample.tsx` layout is a grid of `example`, `controls` and `files` areas, with controls in a right-hand column on large screens and below on small screens. Its props include `component` and "The TS docs for this component". [VisualExample.tsx](https://github.com/adobe/react-spectrum/blob/main/packages/dev/s2-docs/src/VisualExample.tsx)
- **Mantine configurator**: a demo object `{ type: 'configurator', component, code: '<Button{{props}}>Button</Button>', controls: [{ type: 'color', prop: 'color', initialValue: 'blue', libraryValue: 'blue' }, { type: 'size', prop: 'size', … }, { type: 'size', prop: 'radius', … }] }`. `libraryValue` is the component default, so the generated code omits a prop while it equals its default. The control types are Boolean, Color, Number, Segmented, Select, Size and String. [Button.demo.configurator.tsx](https://github.com/mantinedev/mantine/blob/master/packages/@docs/demos/src/demos/core/Button/Button.demo.configurator.tsx), [ConfiguratorDemo/controls](https://github.com/mantinedev/mantine/tree/master/packages/@mantinex/demo/src/ConfiguratorDemo/controls)
- The live Mantine Button page shows controls for variant, color, size, radius, booleans (`fullWidth`, `loading`, `autoContrast`), gradient from/to/degree and justify, and "the generated code updates dynamically". [Mantine Button](https://mantine.dev/core/button/)
- Mantine also has narrow, prop-specific configurators (e.g. `Menu.demo.positionConfigurator`, `Text.demo.linesConfigurator`, `Table.demo.spacingConfigurator`), so a single prop gets its own interactive demo. [mantine repo](https://github.com/mantinedev/mantine/tree/master/packages/@docs/demos/src/demos/core)
- Mantine's Documentation tab has a heading per prop or feature (autoSelectOnBlur, clearable, allowDeselect, searchable, renderOption, …). [Mantine Select](https://mantine.dev/core/select/)
- **MUI**: the API page lists "Demos" back-links to component pages, and the builder injects the demo list into the type-definition JSDoc ("Add demos & API comment block to type definitions"). The link runs component→demos, not prop→demo. [MUI Autocomplete API](https://mui.com/material-ui/api/autocomplete/), [ComponentApiBuilder.ts](https://github.com/mui/material-ui/blob/master/packages-internal/api-docs-builder/src/ApiBuilders/ComponentApiBuilder.ts)
- **Base UI**: the expanded prop row has an **Example** entry (`prop.example`), and every prop row has a stable anchor `#${Part}-${prop}`. This enables deep links from examples or prose to the exact prop. [ReferenceAccordion.tsx](https://github.com/mui/base-ui/blob/master/docs/src/components/ReferenceTable/ReferenceAccordion.tsx)
- **Storybook**: the Controls doc block is a "dynamic table of arg types", and ArgTypes is static. Control types are inferred per type (boolean, `radio`/`select`/`inline-radio`/`check`/`multi-select` for enums, `number`/`range`, `object`/`file`, `color`/`date`/`text`). Autodocs includes the Controls table automatically. [Storybook ArgTypes](https://storybook.js.org/docs/api/arg-types), [Autodocs](https://storybook.js.org/docs/writing-docs/autodocs/)
- **Chakra v3** has an "Explorer" for parts. [Chakra Select](https://chakra-ui.com/docs/components/select)

### Inferences
- The most rigorous pattern combines two of these. Each feature example declares which props it demonstrates (React Aria's `props={[...]}`), and the props table has stable anchors (Base UI's `#Part-prop`). A build step can then (a) link each table row back to the examples that declare it and (b) list props that no example declares. No library observed does (b), and that is the opening umriss would exploit.
- Mantine's `libraryValue` trick (omit a prop from the generated code when it equals the default) is cheap and keeps the code honest. The table's `@default` can be the single source of truth for it.

### Gaps
- I found no library that renders a "used in example X" back-link inside each props-table row. I did not find it in any source read, so the claim that nobody does it is an inference, not a verified finding.
- I did not verify Chakra's "playground" beyond Explorer.

### Takeaway

MUI and React Aria add JS/TS toggles or live editing, and Chakra and Ark add framework tabs.

## Tooling that guarantees completeness: lint/CI gates, coverage

### Takeaway
Completeness is enforced by "generate, then fail CI on diff" pipelines plus generator-side assertions. MUI regenerates prop types and API JSON in CI and fails on `git diff`, and its builder throws on undocumented callback parameter types or returns. TypeDoc's `validation.notDocumented` + `requiredToBeDocumented` and API Extractor's `ae-undocumented` turn missing docs into warnings or errors. None of the libraries observed fails the build when a prop lacks an *example*.

### Cited Findings
- MUI CI runs `pnpm proptypes`, then `pnpm docs:api`, then `git add -A … && git diff --exit-code --staged`, so any undocumented or out-of-date generated API docs fail the build. [MUI .circleci/config.yml](https://github.com/mui/material-ui/blob/master/.circleci/config.yml). The scripts are `"proptypes": "tsx ./scripts/generateProptypes.ts"`, `"docs:api": "… pnpm docs:api:build"`, `"docs:typescript:check"` and `"validate-declarations"`. [MUI package.json](https://github.com/mui/material-ui/blob/master/package.json)
- MUI's builder throws on a callback prop without `@returns` type or with an untyped `@param`, and requires a "single leading jsdoc block" per prop. [generatePropDescription.ts](https://github.com/mui/material-ui/blob/master/packages-internal/api-docs-builder/src/utils/generatePropDescription.ts), [ComponentApiBuilder.ts](https://github.com/mui/material-ui/blob/master/packages-internal/api-docs-builder/src/ApiBuilders/ComponentApiBuilder.ts)
- **TypeDoc**: `validation.notDocumented` "produces warnings for reflections which do not have a documentation comment" and is off by default. `requiredToBeDocumented` lists the kinds that must be documented (Enum, EnumMember, Variable, Function, Class, Interface, Property, Method, …). The other validations are `notExported`, `invalidLink`, `invalidPath`, `rewrittenLink` and `unusedMergeModuleWith`. With `treatWarningsAsErrors` this becomes a gate. [TypeDoc Validation](https://typedoc.org/documents/Options.Validation.html)
- **API Extractor**: `ae-undocumented` ("Missing documentation for ___") is off by default because the API report already marks `// (undocumented)`. Enable it via `messages.extractorMessageReporting["ae-undocumented"].logLevel: "warning"` (or `"error"`). Related messages are `ae-forgotten-export` (a referenced type that is not exported, which would otherwise be unlinkable) and `ae-missing-release-tag`. [api-extractor.json](https://api-extractor.com/pages/configs/api-extractor_json/), [ae-forgotten-export](https://api-extractor.com/pages/messages/ae-forgotten-export/)
- **react-docgen-typescript** `skipChildrenPropWithoutDoc` defaults to true, so undocumented `children` vanish silently unless it is set to false. [react-docgen-typescript](https://github.com/styleguidist/react-docgen-typescript)

### Inferences
- Applied to umriss, the gate set would be: (1) the generator fails when an exported prop has no description, or a callback lacks per-parameter docs, MUI-style; (2) API Extractor's `ae-forgotten-export`, or an equivalent check, catches named types that are referenced but not exported, so every type is linkable; (3) a custom "example coverage" check fails when a prop is declared in no example's `props={[...]}` list (React Aria-style metadata) and carries no `@example`; (4) generated docs are checked in and CI fails on diff.
- `eslint-plugin-jsdoc`'s require-jsdoc rules can also force comments on interface members. I did not verify this in this session, so treat it as a lead.

### Gaps
- I found no public "docs coverage percentage" dashboard in any of the libraries examined.
- I did not verify whether React Aria's or Base UI's docs builds fail on missing prop descriptions.
